- OptimalFS: `fsync` no longer needs a full commit. It appends one batch to an intent log, a ring of blocks set aside at format (1/64 of the volume, 64 KiB to 64 MiB), and flushes once: every namespace and attribute change since the last commit or batch, plus the synced file's inode and changed blocks. Files renamed or linked in those records carry their data along, so a replace-by-rename is never durable without the new file's contents. Another file's dirty data never rides along with an unrelated fsync. Mount replays the log after an unclean shutdown through the ordinary operations with the recorded clock readings, so inode numbers and timestamps come back identical, then commits; a read-only mount replays in memory and writes nothing. When the log can't take a batch (no ring, a full ring, a failed write or flush, a snapshot operation since the last commit) fsync runs a full commit instead. Device work per iteration of a create, write 4 KiB, fsync, rename, directory fsync loop (in-memory device, 4096 blocks): 3.7 blocks written and 2 flushes with the log, 29 blocks and 4 flushes with a commit per fsync. Tests cut power at every write point of random workloads with fsyncs mixed in and require exactly the last durable state, plus hand cases for each durability promise.
