# Optimal OS roadmap

Goal: build the best desktop OS there is, starting with our own kernel written
from scratch: fast, lean, safe, and able to run the software people already use.
The kernel comes first (Phases 0 to 11); the full OS is built on top of it (Phase 12).

This is a serious engineering project, not a toy. That means every phase ends
with a test that proves it is done, every performance claim comes from a
benchmark, and nothing merges unless CI builds it, boots it and passes the tests.

This file is the plan. The detailed design, which every phase below must
meet, is in [design/](design/README.md).

## Pillars, in priority order
1. **Performance.** The main focus. Measured against Linux on the same machine, never guessed ([design/benchmarks.md](design/benchmarks.md)).
2. **Security.** An absolute focus. Nobody can read a user's data remotely, and a compromised app can't reach anything it wasn't given. Exactly what that means, against whom, and how each promise is tested is in [design/threat-model.md](design/threat-model.md).
3. **Lean.** Nothing runs unless something needs it. Small memory footprint, fast boot.
4. **Runs on almost anything.** Any 64-bit x86 PC first, ARM64 later. On hardware that lacks a security feature (no TPM, no IOMMU, BIOS only), Optimal still runs and says plainly which protections that machine can't have.
5. **Compatibility.** Runs existing Linux programs unchanged, 64-bit and 32-bit, which is the road to Windows games through Wine/Proton.
6. **User respect.** The kernel does what the user says. No hidden telemetry, ever.
7. **Polish.** Clear error messages, clean crash reports, good docs.
8. **Customisation.** The smallest pillar: boot options, schedulers and modules the user can choose.

**When pillars conflict.** Security features are on by default. The only
reason to make one optional is a measured cost of more than 2% on the
geometric mean of the desktop benchmark set, or more than 5% on any single
desktop metric, recorded on the scorecard with the owner's sign-off.
Mitigations that stop data leaking between processes, or from the kernel to a
process, are never off by default whatever they cost.

## Core architecture decisions

These are decided now because they are expensive to change later.

- **Language: Rust.** Memory-safety bugs cause most serious kernel security holes. Rust removes most of them at compile time with no speed cost.
- **Shape: a "framekernel".** A small core is allowed `unsafe` code: boot, paging, interrupts, context switching and the raw hardware access. Everything else (scheduler policy, filesystems, network stack, drivers) is written in safe Rust on top of that core. This is a memory-safe in-kernel component architecture: it keeps monolithic-kernel speed (no message passing between processes for every operation) and removes most memory-corruption bugs. It is not a hardware isolation boundary the way a microkernel's separate address spaces are: a safe-Rust component still runs with kernel privilege and can still exhaust resources, deadlock, get logic wrong or misprogram a device, and safe Rust is no defence against a hostile author. So in-kernel code is ours or fully audited, third-party drivers run in their own processes, and isolation comes from the driver trust tiers, resource budgets and per-device IOMMU domains in [design/drivers.md](design/drivers.md). The boundary between the core and the rest is enforced by tools, not convention ([design/core.md](design/core.md)).
- **Compatibility through the Linux system-call interface.** Instead of inventing a new interface and waiting for apps to be written for it, Optimal speaks the same system calls as Linux, 64-bit and 32-bit. Linux programs, Mesa, Wayland and eventually Wine/Proton can then run unchanged. This is our own clean implementation of a public interface, so it involves no Linux code. How Linux semantics sit on top of capabilities is in [design/capabilities.md](design/capabilities.md), and the ABI plan in [design/compat.md](design/compat.md).
- **Boot: our own bootloader, "Optimal Boot"**, a UEFI loader in Rust that speaks the Limine boot protocol, checks a signed config and measures everything into the TPM ([design/boot.md](design/boot.md), `bootloader/DESIGN.md`). Until it ships, Limine (BSD-2-Clause) is used, with every file hash-pinned and its config enrolled, in the shipped image as well as the tests (Phase 1 work, not done yet: the current ISO ships stock, unsigned Limine and enrols nothing).
- **First target: x86_64.** ARM64 comes once the core is stable. Code that depends on the architecture lives in its own module from day one.
- **Licence: our own code only, never GPL.**
  - Kernel, bootloader and every component we write: clean-room code from specs (Intel/AMD manuals, ACPI, PCI, NVMe, xHCI and USB specs, the Linux man pages and uAPI docs for the syscall interface). We never copy, translate or read for reference the code of Linux, BSD or other kernels. Dependencies must be MIT, Apache-2.0, BSD, Zlib or similar, checked by `cargo-deny` in CI.
  - Borrowed programs shipped in the OS until ours replace them: permissive licences preferred; weak copyleft (LGPL, MPL) allowed as separate, unmodified programs (Wine, a browser); GPL programs are not shipped, with one exception: shared libraries under the GCC Runtime Library Exception (glibc is LGPL; libstdc++ and libgcc_s are GPL with that exception), which every Linux program links against ([design/compat.md](design/compat.md)). The base system uses dash as `/bin/sh` and uutils for coreutils; bash and other GPL programs are third-party apps the user can install from the store, never part of the image.
  - Firmware: redistributable vendor binaries (CPU microcode, GPU and Wi-Fi firmware) are allowed as data, each listed with its licence and hash ([design/drivers.md](design/drivers.md)).
  - Test tools: GPL test suites and checkers (LTP, xfstests, kselftest, `e2fsck`) may be run as external test oracles, never linked, vendored or shipped.
  - The repo has no licence file yet, which means all rights are reserved until the owner picks one.

## Security model

Security is built in from Phase 1, not bolted on at the end. The threat model,
the trusted computing base, the hardware security tiers and a table of every
attack path with its defence and its test are in
[design/threat-model.md](design/threat-model.md). In short:

- **Memory safety:** Rust everywhere, with `unsafe` kept to a small, size-capped, inventoried core ([design/core.md](design/core.md)). Memory safety is the floor, not the whole answer: logic bugs, races, hardware misuse and DMA mistakes are handled by the measures below.
- **Driver trust tiers:** core, trusted drivers, restricted drivers (all ours, in the kernel), and user-space drivers (anything third party, and anything parsing untrusted input by default), each with its own IOMMU domain and resource budgets, with defined fault containment and restart ([design/drivers.md](design/drivers.md)).
- **Formal verification of the security-critical core:** proofs and bounded checks at stated levels (Kani, Verus, loom) for page tables, the frame allocator, the soundness of the core's safe APIs, process memory isolation, capability derivation and revocation, user-memory copies, resource accounting, the scheduler, the driver boundary, the IOMMU, storage invariants, network packet parsers and the anti-rollback floor state machine, with the kernel's cryptography tested against published vectors. The `unsafe` hardware shims are a separate, tested-only target with a size cap. Each target states its assurance level (proved, bounded, model-checked or tested only) and its assumptions, and the level reported is the weakest of its own and every target its assumptions rest on ([design/verification.md](design/verification.md)).
- **Hardware protections:** no-execute pages, write-xor-execute for all kernel memory, SMEP/SMAP, UMIP, guard pages around every stack, KASLR with a position-independent kernel randomised over at least 2^16 slots and measured entropy, page-table isolation where the CPU needs it, and the IOMMU from Phase 1. Control-flow protection: user-space CET shadow stacks from Phase 5; kernel shadow stacks and indirect-branch tracking as soon as the stable Rust toolchain can build for them, in Phase 11 at the latest (tracked on the scorecard until then).
- **Least privilege through capabilities:** a process can only touch objects it holds a handle to; Linux file descriptors are capabilities, with a derivation tree and revocation ([design/capabilities.md](design/capabilities.md)).
- **Every app sandboxed by default:** its own view of the filesystem, no access to other apps' data, and access to the camera, microphone, screen, location and user files only through portals whose prompts are drawn by the system (on a dedicated prompt VT reached by Ctrl+Alt+Delete from Phase 5, by the compositor from Phase 7). Apps start with no file or device grants; the default profile includes outbound network only. Network access is a per-identity egress filter that reaches live sockets: a network grant is outbound only, a wildcard socket receives only loopback traffic unless the app holds an inbound grant for that port, and apps holding file grants get no network access unless the user allows that combination.
- **IOMMU on by default from Phase 1:** devices can only reach memory handed to them, interrupt remapping on, external devices need approval. Machines without an IOMMU are told so; there, device-read descriptors hold only typed addresses of granted buffers and DMA-address registers are written only by the core, so driver bugs can't aim DMA at kernel data, but a malicious device or radio firmware can, and radios stay off until the user accepts that named exposure.
- **Encryption by default:** Phase 4a encrypts the disk (AES-XTS, confidentiality only); the own filesystem then adds authenticated, per-user encryption with keys evicted on lock ([design/storage.md](design/storage.md)). Keys are sealed to measured boot with a signed TPM policy plus a PIN where there's a TPM, a passphrase where there isn't, and a recovery key is always created. Every PIN and passphrase is stretched with Argon2id under one rule (memory min(1 GiB, RAM/4) but at least 64 MiB, at least 4 passes), so an encrypted install needs at least 256 MiB of RAM.
- **Verified and measured boot:** firmware checks the bootloader, the bootloader checks a signed config that pins the kernel and the system image's hash tree root, and every step is measured into the TPM. Anti-rollback, A/B slots, boot counting and a recovery image are in [design/boot.md](design/boot.md).
- **Nothing listening by default:** no remote-access services, a default-deny inbound firewall.
- **Lockdown:** no interface lets anyone, root included, load unsigned ring-0 code or read kernel memory ([design/threat-model.md](design/threat-model.md)).
- **Signed updates only,** with a TUF-style key hierarchy, an offline root, a transparency log, reproducible builds and anti-rollback; the update client ships in Phase 7, so the minimum product can be patched.
- **CPU side-channel mitigations** chosen per CPU model after microcode is loaded, including Spectre v1 index masking in safe Rust parsers; SMT is off by default on CPUs affected by MDS, L1TF, TAA or RFDS, and core scheduling is an opt-in for app-to-app isolation only (on by default only where siblings can't leak kernel data); costs benchmarked and published.
- **Testing security like everything else:** every attack path in the threat model has a test that becomes a gate in the phase it lands; continuous syscall, network, device-side and filesystem fuzzing; outside audits of the core at the end of Phases 1, 3, 4a and 4b and before 1.0.

## How we know it is good

- **CI on every change:** build, `rustfmt`, `clippy` with warnings as errors, the in-kernel tests and a boot matrix in QEMU: 64 virtual PCs (BIOS and UEFI, old and new chipsets, 128 MiB to 8 GiB of RAM, 1 to 16 cores), each booted 3 times. Lands in Phase 1: the Rust toolchain pinned to an exact version (not a channel name), Limine and every other download pinned by SHA-256 and GitHub Actions by commit hash, the core's lint rules, the unsafe inventory and core size check, `cargo-deny` and `cargo-vet`, and the gate-table check below. Lands in Phase 1a: the proofs job, with Miri on the host tests of every pure tier-0 crate.
- **Gate tables match the plan** (lands in Phase 1): a CI script checks that every proof target and level change in [design/verification.md](design/verification.md), and every attack row in [design/threat-model.md](design/threat-model.md), is named in the done-when of the phase its table gives, and that no done-when below names a gate those tables put in another phase.
- **No silent skips.** A test that can't run (missing firmware, missing tool) fails CI unless it is on a checked-in allowlist with a reason. A green run means everything listed actually ran. Compatibility pass rates use one skip rule, the same as [design/compat.md](design/compat.md): every skipped test counts as a failure, and a test on the phase's excused list is shown separately and still counts against the rate.
- **Nightly soak:** the same matrix booted 40 times per configuration (over 2,500 boots) to catch rare, timing-dependent bugs. Soak tests grow with every phase: hour-long scheduler stress, file system crash-state runs, driver kill-and-restart loops, continuous fuzzing.
- **In-kernel test suite** (from Phase 1): unit tests that run inside the kernel under QEMU, so allocators, page tables and the scheduler are tested in the real environment.
- **Tough but realistic conditions** (from Phase 1): every change also boots on deliberately awkward machines: CPUs from Core 2 to current Xeon/EPYC with security features missing, 5-level paging, odd core topologies, NUMA (including a node with no memory), odd and split memory, no HPET, no ACPI, old and new OVMF builds, a host fighting for CPU, and Secure Boot attacks (unsigned bootloader, wrong key, tampered kernel, tampered config, old signed image), which must be refused. Fault injection joins as each piece lands: failed allocations, quirky ACPI tables, timer jitter, spurious interrupts, hostile DMA devices, then disk power cuts and I/O errors.
- **Public scorecard from the first bootable build:** performance against a pinned, matched Linux baseline (booted with the same SMT setting, `nosmt` on affected CPUs), measured on dedicated bare-metal machines driven by a separate controller host (shared CI VMs are too noisy and are used for functional tests only); at least 3 runs in each of at least 20 boots per build for every gated metric, with every machine scheduled under 168 hours a week; a release rule (the one-sided 95% upper bound of the geometric-mean difference on the desktop set at most 0.5% worse than the last release, and at most 3% worse on any tracked metric); committed provisional targets that can only tighten; and a security scorecard per hardware tier that counts only what is on in the shipped image. See [design/benchmarks.md](design/benchmarks.md).
- **Formal verification in CI:** every proof target runs on every change, with time budgets and tracked bounds ([design/verification.md](design/verification.md)).
- **Fuzzing:** syscalls from Phase 3, the driver boundary, device-side driver fuzzing, the boot keyboard readers and filesystems from Phase 4a, the pre-cap Optimal header block parser from Phase 4b, each user-space trusted service's protocol (10^8 executions) from the phase it lands in (5 to 7), the network stack, Wi-Fi, Bluetooth and USB from Phase 6.
- **What runs today and what lands later.** Each item above is marked on the scorecard as running now or "lands in Phase N"; nothing is described as running before its job exists.
- **Real hardware:** from Phase 1, each milestone is also checked on at least one real PC booted from USB.

## Phases

Each phase ends with a "done when" test, and every item listed in a phase is
part of that test: if a phase builds something, its done-when checks it. Work
that depends on a phase doesn't ship until that phase's done-when passes.
Work that doesn't depend on it (the built-by-us tracks, proofs, fuzzing,
security items) runs in parallel and is never held back by a later, unrelated
phase. In particular, no security item waits for GPUs or games.
Phases 1 and 4 have lettered parts, and every item of the fourth phase names
its part: 4a (storage) or 4b (trusted boot chain), never both at once.
The file system track starts after 4a.
Each done-when ends by naming the proof targets and their levels, written
own/effective (for example "P/T", or once when both are equal)
([design/verification.md](design/verification.md)) and the attack rows
([design/threat-model.md](design/threat-model.md)) that gate in that phase.

### Phase 0: It boots (done in CI)
- Rust kernel loaded by Limine, writes to the serial port, paints the screen and reports usable memory.
- CI builds the kernel, makes a bootable ISO, boots it in QEMU on BIOS and UEFI, and uploads the ISO.
- Done when: CI is green and the ISO boots on a real PC from a USB stick, showing the blue screen band.

### Phase 1: The core
- **1a, CPU setup:** GDT, TSS, IDT, and handlers for every CPU exception with a clear crash report (registers and a stack trace); a double-fault handler on its own IST stack so stack overflows are reported; the proofs CI job and Miri land.
- **1b, memory:** physical frame allocator (NUMA-aware), our own page tables for the kernel, a fallible kernel heap, guard pages; the kernel built position-independent, picking its own virtual base over at least 2^16 slots at 2 MiB granularity, and its direct-map base, when it builds its own page tables (KASLR, the same under Limine and Optimal Boot); its physical load address is chosen by the loader, and under Limine the scorecard reports physical KASLR as "not done until Optimal Boot"; the first proofs of memory targets.
- **1c, ACPI, interrupts, IOMMU and time:** ACPI tables, AML hosting staged as in [design/drivers.md](design/drivers.md) (safe Rust, fuzzed, confined), minimal PCI enumeration (enough to find and program the IOMMU), local APIC and I/O APIC, the IOMMU in deny-all mode (every unused Intel context entry and all 65,536 AMD-Vi device table entries per segment blocking DMA and interrupts) with interrupt remapping, and bus mastering cleared on every bridge and root port and then every function in the defined order ([design/drivers.md](design/drivers.md)), kept off until assigned. DMA is stopped by the bridge or root-port Bus Master Enable plus the IOMMU, never by a device's own BME. Exempt: the IOMMU's own function, the firmware display and the bridges on its path, and USB host controllers, which stay with the firmware (BME on, in a domain holding only their RMRRs) until the Optimal driver that runs them starts. BME stays clear on every Thunderbolt downstream port and hotplug-capable port. Boot-services and bootloader-reclaimable memory is not reused until bus mastering is cleared and the IOMMU is live. A machine with no firmware pre-boot DMA protection shows the named "boot DMA window" exposure. Time: a TSC invariance check, calibration from CPUID leaves 15h/16h, else HPET or the ACPI PM timer, else the PIT, and a clocksource watchdog; timer events from the LAPIC TSC-deadline mode, falling back to LAPIC one-shot, HPET, then PIT; the clock-drift exchange on the 16550 UART. Microcode loaded on the boot CPU before mitigations are chosen.
- **1d, console:** a framebuffer text console so the kernel can talk without serial (with a font we make or that is permissively licensed).
- The kernel becomes a workspace with tier-0 crates and enforced lint rules, the unsafe inventory and the core size cap ([design/core.md](design/core.md)).
- Security baseline: no-execute, write-xor-execute kernel mappings, SMEP, SMAP, UMIP, guard pages, KASLR. The shipped image moves to the hash-pinned, enrolled Limine chain (not done yet: the current ISO ships stock, unsigned Limine and enrols nothing), keeping the BIOS image for B4, with a CI check that fails the release build unless the ISO's `limine.conf` hash is enrolled in its Limine binary. Supply chain: the exact toolchain version, Limine's SHA-256 and every other build input pinned.
- In-kernel test runner in CI, plus the tough-conditions run and Secure Boot attack tests. The "old signed image refused" test puts the old image's hash in dbx in the test OVMF variable store, because Limine has no security version number.
- The hostile-device emulator: our own vfio-user device server (permissively licensed, built on libvfio-user), attached to an unmodified QEMU at a pinned version used as an external test tool.
- First scorecard entries: boot time, timer accuracy, kernel memory, and the security table.
- Where it runs today: CI covers QEMU boots, the in-kernel tests and proofs as each lands; real-hardware and bare-metal items are reported "not yet measured" until the owner's machines are online.
- Done when: every exception type is triggered on purpose in tests and reported correctly; the allocator and page tables pass their tests; every tough-conditions scenario passes; the KASLR tests in [design/boot.md](design/boot.md) pass (an SP 800-90B estimate of at least 9 bits for the picker's output over 10^6 host draws, a 90B estimate for each raw source: EFI_RNG, RDRAND/RDSEED and the TSC fallback; and at least 95 distinct bases in 100 QEMU boots); boot time from firmware handoff to kernel ready is under 300 ms on the reference desktop; the timer drifts under 1 part per million over a 10-minute run on KVM, with QEMU's explicit `tsc-frequency` read by the guest from CPUID 15h, measured as the least-squares slope of the kernel's once-a-second clock lines on the 16550 UART (polled, no DMA) against their arrival times taken on the host with `CLOCK_MONOTONIC_RAW` (never against the calibration source; the bare-metal drift test is in Phase 2); the Secure Boot attack tests refuse an unsigned bootloader, a wrong key, a tampered kernel, a tampered config and an old signed image (through its dbx hash entry); the release build's enrolment check runs; QEMU `usb-ehci` and `piix-uhci` controllers stay with the firmware, BME on, in a domain holding only their RMRRs; the boot DMA window is reported on OVMF without pre-boot protection; the gate-table check runs; and the outside audit of the Phase 1 core is done with its findings fixed. Proof gates: target 3a at B per tier-0 API and target 3b at T for each shim, from 1a; target 1 at B/T and target 2 at B/T (owners: allocator and page tables), at 1b; target 10 at B/T, at 1c. Attack rows: A4 → poisoned dependency; A5 → DMA attack (1c: the vfio-user hostile device server on QEMU `intel-iommu` and `amd-iommu`, on the root bus and behind a root port, sending DMA and MSI writes outside its domain and from an unassigned requester ID, compatibility-format MSIs and DMA across the firmware hand-off).

### Phase 2: Many cores and a scheduler
- Start every CPU core (SMP), with per-core data, microcode on every core, and the typed locking and per-CPU rules in [design/core.md](design/core.md), checked by a lock-order checker.
- The scheduler in [design/scheduler.md](design/scheduler.md): fully preemptible kernel, real-time, fair (EEVDF) and idle classes, threaded interrupt handlers, priority inheritance for kernel locks, topology and capacity-aware placement for hybrid CPUs, high-resolution timers, a tickless idle and the single-thread tick stop (a CPU running one thread stops its tick).
- Frequency control with hardware P-states (Intel HWP, AMD CPPC). From here it is a precondition of every comparison with Linux, the Phase 4a storage set included. Microbenchmarks run with turbo off and HWP or CPPC minimum = maximum = 80% of guaranteed performance on both kernels; desktop, real-time-latency and throughput metrics run at shipped defaults with the same energy-performance preference on both.
- Kernel threads, sleeping, wake-ups and timers.
- The latency tracer, whose trace points switch between their two precompiled states through the core's text-poke path (a temporary private writable mapping, the `int3` and IPI cross-modifying-code protocol, direct-map aliases of kernel text read-only).
- The benchmark harness lands here, with Optimal compared against **itself** only (there is no user space yet to compare with Linux fairly), plus the first dedicated bare-metal runner and its rig ([design/benchmarks.md](design/benchmarks.md)): a controller host, not the machine under test, boots the runner over UEFI HTTP or PXE, power-cycles it through a relay and on a watchdog, and captures checksummed results over serial; it carries a GPS receiver whose PPS pulse drives each runner's UART DCD pin; only maintainer-approved commits run, on an isolated network with no secrets. `isolcpus` is used only for the per-change microbenchmark tier; every desktop, real-time-latency and throughput metric runs on the default boot with no isolated CPUs. Microbenchmark runs during which an SMI arrived are discarded and rerun; tail-latency runs keep every sample and publish the SMI count.
- Done when: all cores run stress tests for an hour with no crash, deadlock or lock-order report; the latency tracer finds no non-preemptible section over 50 µs on the bare-metal runner (report-only in VMs), excluding SMI-overlapped sections, which are counted and published; a trace point toggled under load on every CPU causes no fault and no mixed state; the priority-inheritance chain, capacity-aware placement, tickless idle (no periodic tick on an idle CPU over 10 s), single-thread tick stop (at most 10 timer interrupts in 10 s on a CPU running one spinning thread), isolated-CPU interrupt count (0 on isolated CPUs) and timer accuracy tests in [design/scheduler.md](design/scheduler.md) pass; on bare metal the timer's drift against the PPS pulse, timestamped from the DCD modem-status interrupt, is published and at most 50 ppm; real-time wake-up latency with all cores saturated (a spinning thread per CPU plus IPI and timer storms) meets P99 < 50 µs and P99.9 < 100 µs on the reference desktop, run from the controller host. Proof gates: target 1s at M/T; target 3a at M for interrupt re-entry (B+M from here); target 3b at T for the text-poke shim; target 7 at B/T for scheduler CPU accounting; target 8 at M/T for run queues and priority inheritance (loom) and at B for real-time throttling (Kani over an abstract clock); target 10 at M/T for the invalidation-before-free order; target 11 at M/T. Attack rows: none.

### Phase 3: User space
- Ring 3, processes and threads with the Linux task model, their own address spaces, ELF loading (static, static-PIE and dynamic), the full auxiliary vector and a vDSO, system calls, per-thread signals with XSAVE-sized frames, 64-bit **and 32-bit** entry paths ([design/compat.md](design/compat.md)).
- Virtual memory features programs need: `mmap`, copy-on-write `fork`, demand paging, PCID (6 dynamic slots per CPU, [design/scheduler.md](design/scheduler.md)), page-table isolation where the CPU needs it.
- A minimal virtual filesystem layer, an initramfs unpacked into a RAM filesystem, and mount namespaces, so per-app file views exist from the start.
- The capability system with derivation and revocation, Linux fds as capabilities to shared open file descriptions (offset, status flags and locks shared by `dup`, `fork` and `SCM_RIGHTS`; revocation acts on the description), kernel-attested app identity, per-app file views, the default app profile and the lockdown table ([design/capabilities.md](design/capabilities.md)).
- Syscall entry hardened against Spectre-style attacks, including index masking; SMT off by default on CPUs affected by MDS, L1TF, TAA or RFDS (listed in the mitigation matrix), with core scheduling as an app-to-app opt-in there and the default only on CPUs whose siblings can't leak kernel data. Syscall fuzzing starts. Verus starts.
- Done when: static glibc and static musl programs (64 and 32 bit) and the milestone 1 suite (with the single-threaded gVisor subset) run unchanged; the lockdown test passes with every attempt refused; published Spectre and Meltdown proof-of-concepts, and the cross-hyperthread leak test on the shipped SMT default of each CPU model in the matrix and separately with SMT on and core scheduling opted in, recover zero bytes over 10^6 attempts; an unknown-syscall sweep returns `ENOSYS` for every unimplemented number; the latency tracer costs at most 0.5% on the syscall round-trip microbenchmark when off; and the outside audit of syscall entry, user copy and capabilities is done. Proof gates: target 1 at P/T; target 1s re-gated at M/T (PCIDs and user address spaces); target 2's owner kinds extended to memory objects; target 4 at P/T for the sharing paths that exist in Phase 3, with the CI check that nothing but the single `core-mm` user-PTE API reaches the PTE-writing shim; target 5 at P/T, including open file descriptions, with its per-syscall test at T; target 6 at B/T. Attack rows: A3 → kernel (syscall fuzzing, proof targets 4 to 6, the lockdown test); A3 → side channels.

### Phase 4a: Storage and files
- PCI enumeration with AER/DPC and hotplug (Completion Timeout set to range A, at most 10 ms, on every device that supports it; no MMIO read with interrupts off), then NVMe and AHCI drivers on the driver framework: trust tiers, the message interface, budgets, fault containment and restart, the driver watchdog (a forced-preemption IPI, then park at core-call depth 0 or on core exit), `suspend`, `resume` and `reset` callbacks, device-side fuzzing ([design/drivers.md](design/drivers.md)). The AML interpreter moves under the tier-2 framework. virtio-blk runs in tier 2. NVMe and AHCI start in tier 1, each with its own controller reset path (NVMe Abort, then CC.EN=0 and re-initialisation; AHCI COMRESET) that re-sends through the replay log, because a device hang is not a driver hang, and must meet the promotion thresholds for in-kernel parsers before this phase closes. Streaming maps lend page-cache and `O_DIRECT` pages to a device with a recorded DMA pin. On machines without an IOMMU (D2), `DmaBuffer`s and rings come from a dedicated DMA region and only streaming maps are bounced; descriptor memory a device reads is built only from typed addresses of granted buffers, and DMA-address registers (NVMe admin queues, ring bases, DCBAAP) are written only by the core from a `DmaBuffer`; tier-3 drivers rely on the IOMMU alone.
- Unlock input before Phase 6: a PS/2 keyboard driver and serial keyboards, and a polled xHCI boot-protocol keyboard reader, both in tier 1 and each meeting the promotion thresholds for its parser. The reader parses only 8-byte boot reports, takes over only its own controller, writes Intel's `XUSB2PR` and `USB3_PSSEN` port routing when it starts, and stops when the Phase 6 xHCI driver binds. EHCI, OHCI and UHCI controllers stay with the firmware until Phase 6.
- The block layer with flush/FUA and completion ordering, the durability contract, the page cache with stable pages and copy-on-write space reservation ([design/storage.md](design/storage.md)). Error policy: a write failing with a retryable status is retried 3 times, the last after a controller reset; a non-retryable status is not retried; a device is set read-only, never hidden, when 16 writes have failed all retries within 10 minutes, or at once when it reports itself read-only. A per-device replay log keeps completed, unflushed writes for re-sending after a restart or controller reset.

- Disk encryption stage 1 (LUKS2, AES-XTS) with a passphrase typed on the framebuffer console and a 256-bit recovery key. Every key slot except the recovery key's uses Argon2id with 4 lanes, memory = min(1 GiB, RAM/4) but at least 64 MiB, and at least 4 passes, raised until unlocking takes about 2 s on that machine, with the parameters stored per key slot; the installer refuses an encrypted install below 256 MiB of RAM. All cipher, hash and KDF code is the `core-crypto` crate, capped at 4,000 lines separately from the 3,000-line shim cap, using verified generated code wherever it exists for the algorithm and instruction set.
- The read-only, hash-tree-verified system image format with A/B slots.
- Filesystem testing: the crash-state model and oracle in [design/storage.md](design/storage.md) (for ext4, each crash state is mounted by Optimal, which replays the journal, then `e2fsck -fn` must be clean, and Linux's replay of a copy must give the same tree), property tests against a reference model, image fuzzing (including LUKS2 headers), long randomised workloads, all running forever in the nightly soak.

### Phase 4b: The trusted boot chain
- Entry conditions: Optimal Boot's measured boot and boot counting have landed (bootloader track), and Secure Boot path 2 works on the reference laptop.
- The TPM 2.0 driver: MMIO and the TPM service in tier 0, the protocol in a safe tier-1 crate. The TPM service lives in the kernel and alone holds raw TPM access; user space reaches the TPM only through the TPM broker API. The signed TPM policy over PCR 4 (path 1 and path 2 variants), 7, 8 and 9, PIN and recovery, TPM ownership, with parameter encryption ([design/boot.md](design/boot.md)). Optimal Boot measures its own security version number, then the config-signing key ID, into PCR 8. The PIN is stretched under the KDF rule of Phase 4a and mixed into the key; on firmware-TPM machines a passphrase of at least 60 estimated bits is required instead. Optimal Boot reads the PIN through UEFI `ConIn` before `ExitBootServices`, above an anti-phishing TOTP code (RFC 6238) from a sealed HMAC key that the user checks against their phone.
- Optimal Boot accepts only configs signed by the config-signing key: offline, held 2-of-3 on hardware tokens as a delegated TUF role, its public half built into the loader, revoked by a loader with a higher SVN. Before `ExitBootServices` the loader sets up a deny-all IOMMU (PMRs where it can't program translation) and disables the platform hierarchy if the firmware left it open.
- Sealing happens at the first boot from disk, never in the installer: the installer sets up TPM ownership and the counter and writes an empty Optimal header block; the first boot unlocks with the recovery key, replays its own PCR 4 and PCR 7 log, picks the PCR 4 variant and seals; the second boot test-unseals with the PIN alone.
- The Optimal header block is the only part of the data volume read before capping: the last 16 KiB before the LUKS2 data offset, which is fixed at 16 MiB, in two 8 KiB copies, each with a version and a CRC-32C, holding the KDF parameters, the SRK and base-index names, the volume tag and the sealed blobs in fixed 512-byte slots. The volume tag (HMAC-SHA-256 over the raw LUKS2 header area and the header block's fields) is checked before any JSON is parsed. Its parser is fuzzed to the in-kernel thresholds.
- PCRs 8 and 9 are capped unconditionally, whatever the unseal result (passphrase fallback included), before any byte of the data volume beyond the Optimal header block is parsed; the LUKS2 JSON and the volume map are parsed only after capping. One list of sealed objects: the disk secret, the service-key secret S, the anti-phishing TOTP key, the hibernation key and the resume object (Phase 10). S carries `TPM2_PolicyAuthValue` (the stretched PIN) and is unsealed only after the volume tag matches. The hibernation key is a random image key generated each boot before capping, sealed with the full disk policy and kept in kernel memory. Objects used after capping (per-user home keys and the storage replay counter) carry `TPM2_PolicySecret` against the service key, so only a kernel that passed the pre-cap check can use them.
- Anti-rollback: the floor is the NV counter's value minus a base kept in a write-once NV index locked at install, and the counter's authPolicy uses `TPM2_PolicyAuthorize`, so the disk policy key can rotate. Raising it takes two boots: after the health check, user space writes the other slot and both copies of the recovery image at the new SVN, verifies them, and writes a "commit SVN n" request into loader state; on the next boot the kernel (B1, before capping) or the loader (B2) raises the floor. On B1 the kernel reseals every sealed object at the new floor, test-unseals each, writes the set into the other header-block copy, and only then increments the counter; a boot that resumes from hibernation leaves the request pending. Every predicted PCR 7 reseal (dbx, db, firmware, shim or SbatLevel) reseals every listed object the same way. On B2 machines (no TPM) the floor is a boot-services-only UEFI variable; if it is missing or corrupt the floor is the highest SVN among the configs on the ESP, and the scorecard says B2 anti-rollback holds against OS-level attackers only (against physical ones only with owner keys).
- TPM clear detection: the SRK name and the base-index name are recorded in loader state and the header block; if either changes, the loader boots only the highest-SVN image present and warns.
- Two loader directories, each with its own `Boot####` entry, plus the `\EFI\BOOT\BOOTX64.EFI` fallback: an update writes the inactive directory, verifies it and only then flips `BootOrder`; an SBAT or dbx revocation is applied only after both directories and the fallback carry the new generation.
- Done when: the TPM tamper and rollback tests in [design/boot.md](design/boot.md) pass under swtpm and on the reference laptop, including: unsealing across a kernel update, an OS-applied dbx update and an SBAT bump with a new shim; refusal of a tampered loader, config, command line, kernel, module or system-image root hash, an older signed Optimal Boot, a signed EFI tool replaying the published PCR 8 and 9 events, and a config signed by a revoked key; an install from USB through shim onto a disk that then boots by path 2, and the reverse, sealing at the first boot and unsealing at the second with no recovery prompt; a pre-incremented swtpm counter; a floor raise across a reboot; no increment possible after capping; a power cut at every step of a raise (each slot write, each recovery copy, the request, the reseal and test-unseal of each sealed object, each header-block write, each increment) and at each loader-directory write, the `BootOrder` flip and the fallback copy, booting each time without the recovery key; after a floor raise and after an OS-applied dbx update, a stand-in object created after capping under `PolicySecret` unseals, the anti-phishing code is correct and that boot's hibernation key unseals before capping (the same suite reruns with a real second-user login in Phase 5 and a real hibernate and resume in Phase 10); the OS unable to write the B2 floor variable, and a deleted variable giving the highest SVN on the ESP; booting the recovery image after a raise; a substituted data volume refused before its JSON is parsed; a cleared TPM with redefined indices making the loader boot the newest image, warn and show no code; a flipped block in the active slot making the loader fall back to the other; Optimal Boot's deny-all IOMMU or PMR set-up blocking DMA from the vfio-user emulator and from the FPGA board between `ExitBootServices` and the kernel's IOMMU setup; the pre-cap header parser fuzzed to the in-kernel thresholds; and the outside audit of the TPM service, the loader and the core's changes since Phase 3 is done. Proof gates: target 16 at B. Attack rows: A6 → tamper with the boot chain; A6 → substituted volume; A6 → clear the TPM to reset the floor; A6 → TPM bus; A6 → guess the PIN.

### Phase 5: Running real Linux programs
- Before this phase starts, the desktop benchmark set is frozen and versioned, and the reference desktop's discrete GPU model is fixed and recorded, so the locked machine state doesn't change afterwards.

Each phase's pinned test list and excused list are frozen when the phase starts; removing a test or adding an excuse needs the owner's sign-off.
- Scheduling ABI (policies, affinity, cgroup CPU control, the `sched_attr.sched_runtime` slice), pressure information, compressed swap, transparent huge pages and INVLPGB broadcast shootdowns, user-space shadow stacks, io_uring (milestone 5).

D-Bus proxies and per-app keyrings are mediated from here. Every trusted service that sends traffic for an app (open-URI, notifications, the email portal) checks the caller's grants: open-URI with a non-file scheme from an identity without outbound network shows a prompt naming both apps and the full URL.
- App identity: an unpackaged program's identity is its path plus the SHA-256 of its launch closure (an interpreter plus the script's hash, plus the full argv for `-c` style calls; an ELF program's `PT_INTERP` and every library it maps from outside the system image; an AppImage file). The whole install directory of a granted unpackaged app is protected, and grants carry across an update only if every changed file was written by the app itself. The protected launch paths include `~/.local/share/dbus-1/services`, `~/.config/systemd/user`, `~/.config/environment.d`, `~/.config/mimeapps.list` and autostart, and the service manager and D-Bus activation apply provenance. Executables written by an app carry that provenance and get no network on first desktop launch until the user is asked; a terminal-identity process that executes a file another app wrote gets `EACCES` until the user approves it. Only the launcher and the service manager hold the capability to spawn a process with an identity, and children get at most their parent's grants.
- The terminal: `TIOCSTI` returns `EPERM`, `TIOCLINUX` is absent, the launcher gives a fresh pty whenever it starts a different identity, terminals ignore OSC 52 and report sequences from foreign identities, and a writable grant inside the terminal's home is a direct channel to the terminal (its prompt says "can run code as Terminal").
- Direct channels: identities joined by any channel in the closed list `design/channels.toml` (cross-identity loopback connections included; the OAuth loopback auto-grant applies only if the requester already holds network) are checked as one principal, transitively, through a per-session union-find that splits only at logout.
- Per-app private homes: each identity gets a persistent writable home (a protected path, `~/.var/app/<id>`) mounted as `$HOME` with the `XDG_*` variables set into it, plus a published read-only list of shared settings; the terminal identity keeps the real home minus the protected paths.
- The app manifest format and the launcher's manifest reader; the Flatpak launcher (a trusted service with its own conformance tests, refusing the `org.freedesktop.Flatpak` talk-name); and the document portal, a tier-3 file system mounted in every view with per-app entries, persistence and revocation, with toolkits forced onto portal dialogs where they can be.
- Per-user home encryption: each user's home lives in per-user extents of an in-kernel volume map on the outer encrypted device, encrypted only by that user's key, which the TPM service unwraps after the PCRs are capped ([design/storage.md](design/storage.md)). The map is authenticated with a key derived from the system volume key and parsed only after capping.
- Run BusyBox, a shell, then real tools like Python, GCC, git and SQLite.
- First non-storage benchmarks against Linux, with identical binaries on both and HWP/CPPC (from Phase 2) configured the same on both kernels.
- Done when: each milestone's suite reaches its published target pass rate with results reported by outcome (target 90% for the pinned LTP syscall list, with every skipped test counted as a failure and excused tests shown separately and still counted against the rate, and 100% for security-related tests, each matching its checked-in expectation file exactly); a Steam Runtime container runs under `bwrap`; Chromium's sandbox self-test passes; rootless `podman run` works with pasta and with slirp4netns networking; the Flatpak launcher's conformance tests and upstream `flatpak run` tests pass; the hostile tests in [design/capabilities.md](design/capabilities.md) pass: widening an fd through its open file description, `/proc/self/fd` reopen or a cross-identity `..` (`EXDEV`), escaping a mount namespace, and forging an app identity; the golden first-run test passes (Wine, Steam, Firefox and git create the same paths under `$HOME` as on Linux); on a B1 machine a second user logs in after the PCRs are capped and gets their key, and the Phase 4b sealed-object suite reruns with that real login (both run once 4b is done); every entry of the storage set rerun on a per-user home volume is within 10% of the same entry on the system volume path; real-time wake-up latency under hackbench, a pinned compile, fio on NVMe and memory pressure together meets P99 < 50 µs and P99.9 < 100 µs; and context-switch, wake-up, messaging and `fork`+`exec` with 10, 10^4 and 10^5 open fds are within 10% of matched Linux on the reference desktop. blended number) go on the scorecard. The full table, the ABI decisions
(32-bit support, kernel identity, `ENOSYS` for anything missing, io_uring and
eBPF) and the measurement rules are in [design/compat.md](design/compat.md).

## Built by us: our own stack

These pieces will be written by us, from specs, instead of borrowed. Each one
runs as its own track alongside the kernel phases, and starts once the kernel
can support it. Until ours is ready, the borrowed version (where one exists)
keeps things working.

| Piece | Starts after | Replaces | Done when |
|---|---|---|---|
| Bootloader (Optimal Boot) | Phase 1 | Limine | Boots Optimal on UEFI across the full CI boot matrix and on 3 real PCs; signed config, measured boot and the tamper tests pass; Secure Boot paths per [design/boot.md](design/boot.md) (owner keys working on 3 PCs, shim submitted for review); parsers fuzzed. BIOS support is a later, separate item |
| Filesystem | Phase 4a | ext4 as the default | Copy-on-write with authenticated encryption, checksums and snapshots (a user feature; OS rollback uses the A/B image); at least 10^7 crash states per night pass the oracle in [design/storage.md](design/storage.md), with lying-drive flush drops 1 to K commits back (K = 8 commits or 30 s, whichever is longer) mounting at the last commit before the drop, plus 1,000 real power cuts on at least 3 drive models; whole-volume replay refused on B1, with power cuts around the replay-counter bump mounting; fsck, scrub and rescue tools ship with format v1; beats matched ext4 on the aged storage benchmark set, `fsync` latency under background writeback included. Proof gates: target 12c at B, probabilistic. Attack rows: A6 → tamper with ciphertext (stage 2: bit flips detected); A6 → locked or suspended laptop (after lock, no protected-class key or plaintext canary in memory) |
| Compositor | Phase 7 | Borrowed Wayland compositor | Speaks the Wayland protocol so existing apps run; tear-free, variable refresh rate, and input-to-display latency P99 and P99.9 lower than the best of KWin, Mutter and Sway on the reference desktop in the benchmark harness |
| Desktop | Compositor | Borrowed desktop shell | Panel, launcher, notifications, built-in tiling and gaming mode, all within the total OS memory target in [design/benchmarks.md](design/benchmarks.md) |
| Settings app | Desktop | Separate config tools | One app controls everything, with no terminal needed for any common task (a published list of tasks, each tested) |
| Store | Desktop + networking | Borrowed store | One store and one package format, with signed packages, atomic installs and rollback |
| Everyday apps | Desktop | Borrowed apps | Files, terminal, text editor, image viewer, media player, calculator and system monitor |
| Web browser engine | Phase 7 | Borrowed browser | Passes at least 90% of the Web Platform Tests subsets for HTML, CSS and DOM that the major engines all pass, runs a JavaScript engine that passes test262 at 95%, and renders the 50 most-visited sites with no blocking bug |

**Minimum product.** The kernel through Phase 7 with every security gate
passing (signed updates included), the bootloader, and borrowed userland is a complete, usable,
secure OS. Everything after that improves it. If time runs short, the order
of priority is: kernel phases and their security gates, then the bootloader
and filesystem tracks, then GPU and games, then the other tracks.

**Defer rules.** Every track reports one progress metric (for the browser
engine, its WPT pass rate; for the compositor, its latency against the best
borrowed one). A track whose metric hasn't moved in 12 months is paused and
its borrowed replacement stays, until there's a plan to unblock it. No track
is ever shipped before it meets its done-when, whatever that costs in time.

Honest notes:
- **Bootloader** and **everyday apps** are the most achievable.
- **Filesystem** is very hard to get right, because a bug loses people's files. It gets the heaviest testing of anything here.
- **Web browser engine** is the biggest single project on this list, bigger than the kernel. HTML, CSS and JavaScript each take years. It is a long-running track, and a borrowed browser ships until ours passes its tests.

## What only the owner can provide

Some things can't be done from CI and need Ben:

- **Real hardware:**
  - booting each milestone from USB on a real PC;
  - the reference machines in [design/benchmarks.md](design/benchmarks.md), set up as dedicated runners for the performance gate: the reference desktop by Phase 2, a second identical reference desktop by Phase 6 (long runs, starting with the 24-hour audio runs), the rest by Phase 5;
  - the reference desktop's discrete GPU model chosen and recorded before Phase 5 starts (the Phase 8 driver targets it);
  - the benchmark controller host (a Raspberry Pi or similar, with a power relay, serial capture, an isolated network, and a GPS receiver whose PPS output is wired to each runner's UART DCD pin for the bare-metal clock-drift test) by Phase 2;
  - a multi-node reference machine (2-socket, or an AMD EPYC in NPS2 or NPS4) as soon as it can be had, until which NUMA is tested for function only;
  - by Phase 4a: a PCILeech-class FPGA DMA board, run in a D1 reference machine whose firmware has pre-boot DMA protection; an Intel 7- or 8-series machine for the USB port-routing test; a relay power-cut rig and 3 drive models (ext4 over LUKS2 in 4a, then the filesystem track);
  - an input-latency rig (USB HID microcontroller and photodiode) by Phase 7.
- **Signing keys:** hardware tokens for the offline root key (2 of 3) before the first public release, and for the config-signing key (2 of 3) by Phase 4b.
- **Outside audits** at the end of Phases 1, 3, 4a and 4b and before 1.0 (volunteers or funding).
- **Accounts:** shim review submission and Microsoft signing, and repository settings.

Until a dependency arrives, the work that needs it is reported as "not yet
measured" or "not yet done", never claimed.

## What we deliberately don't build
- A compiler (Rust/LLVM), and for now the GPU graphics stack (Mesa) and Windows compatibility (Wine/Proton). Those run through the Linux interface and can become "built by us" tracks later.
