# Optimal OS roadmap

Goal: build the best desktop OS there is, starting with our own kernel written
from scratch: fast, lean, safe, and able to run the software people already use.
The kernel comes first (Phases 0 to 11); the full OS is built on top of it (Phase 12).

This is a serious engineering project, not a toy. That means every phase ends
with a test that proves it is done, every performance claim comes from a
benchmark, and nothing merges unless CI builds it, boots it and passes the tests.

This file is the plan. The detailed design, which every phase below must
meet, is in [design/](design/README.md).

## Pillars, in priority order
1. **Performance.** The main focus. Measured against Linux on the same machine, never guessed ([design/benchmarks.md](design/benchmarks.md)).
2. **Security.** An absolute focus. Nobody can read a user's data remotely, and a compromised app can't reach anything it wasn't given. Exactly what that means, against whom, and how each promise is tested is in [design/threat-model.md](design/threat-model.md).
3. **Lean.** Nothing runs unless something needs it. Small memory footprint, fast boot.
4. **Runs on almost anything.** Any 64-bit x86 PC first, ARM64 later. On hardware that lacks a security feature (no TPM, no IOMMU, BIOS only), Optimal still runs and says plainly which protections that machine can't have.
5. **Compatibility.** Runs existing Linux programs unchanged, 64-bit and 32-bit, which is the road to Windows games through Wine/Proton.
6. **User respect.** The kernel does what the user says. No hidden telemetry, ever.
7. **Polish.** Clear error messages, clean crash reports, good docs.
8. **Customisation.** The smallest pillar: boot options, schedulers and modules the user can choose.

**When pillars conflict.** Security features are on by default. The only
reason to make one optional is a measured cost of more than 2% on the
geometric mean of the desktop benchmark set, or more than 5% on any single
desktop metric, recorded on the scorecard with the owner's sign-off.
Mitigations that stop data leaking between processes, or from the kernel to a
process, are never off by default whatever they cost.

## Core architecture decisions

These are decided now because they are expensive to change later.

- **Language: Rust.** Memory-safety bugs cause most serious kernel security holes. Rust removes most of them at compile time with no speed cost.
- **Shape: a "framekernel".** A small core is allowed `unsafe` code: boot, paging, interrupts, context switching and the raw hardware access. Everything else (scheduler policy, filesystems, network stack, drivers) is written in safe Rust on top of that core. This is a memory-safe in-kernel component architecture: it keeps monolithic-kernel speed (no message passing between processes for every operation) and removes most memory-corruption bugs. It is not a hardware isolation boundary the way a microkernel's separate address spaces are: a safe-Rust component still runs with kernel privilege and can still exhaust resources, deadlock, get logic wrong or misprogram a device, and safe Rust is no defence against a hostile author. So in-kernel code is ours or fully audited, third-party drivers run in their own processes, and isolation comes from the driver trust tiers, resource budgets and per-device IOMMU domains in [design/drivers.md](design/drivers.md). The boundary between the core and the rest is enforced by tools, not convention ([design/core.md](design/core.md)).
- **Compatibility through the Linux system-call interface.** Instead of inventing a new interface and waiting for apps to be written for it, Optimal speaks the same system calls as Linux, 64-bit and 32-bit. Linux programs, Mesa, Wayland and eventually Wine/Proton can then run unchanged. This is our own clean implementation of a public interface, so it involves no Linux code. How Linux semantics sit on top of capabilities is in [design/capabilities.md](design/capabilities.md), and the ABI plan in [design/compat.md](design/compat.md).
- **Boot: our own bootloader, "Optimal Boot"**, a UEFI loader in Rust that speaks the Limine boot protocol, checks a signed config and measures everything into the TPM ([design/boot.md](design/boot.md), `bootloader/DESIGN.md`). Until it ships, Limine (BSD-2-Clause) is used, with every file hash-pinned and its config enrolled, in the shipped image as well as the tests (Phase 1 work, not done yet: the current ISO ships stock, unsigned Limine and enrols nothing).
- **First target: x86_64.** ARM64 comes once the core is stable. Code that depends on the architecture lives in its own module from day one.
- **Licence: our own code only, never GPL.**
  - Kernel, bootloader and every component we write: clean-room code from specs (Intel/AMD manuals, ACPI, PCI, NVMe, xHCI and USB specs, the Linux man pages and uAPI docs for the syscall interface). We never copy, translate or read for reference the code of Linux, BSD or other kernels. Dependencies must be MIT, Apache-2.0, BSD, Zlib or similar, checked by `cargo-deny` in CI.
  - Borrowed programs shipped in the OS until ours replace them: permissive licences preferred; weak copyleft (LGPL, MPL) allowed as separate, unmodified programs (Wine, a browser); GPL programs are not shipped, with one exception: shared libraries under the GCC Runtime Library Exception (glibc is LGPL; libstdc++ and libgcc_s are GPL with that exception), which every Linux program links against ([design/compat.md](design/compat.md)). The base system uses dash as `/bin/sh` and uutils for coreutils; bash and other GPL programs are third-party apps the user can install from the store, never part of the image.
  - Firmware: redistributable vendor binaries (CPU microcode, GPU and Wi-Fi firmware) are allowed as data, each listed with its licence and hash ([design/drivers.md](design/drivers.md)).
  - Test tools: GPL test suites and checkers (LTP, xfstests, kselftest, `e2fsck`) may be run as external test oracles, never linked, vendored or shipped.
  - The repo has no licence file yet, which means all rights are reserved until the owner picks one.

## Security model

Security is built in from Phase 1, not bolted on at the end. The threat model,
the trusted computing base, the hardware security tiers and a table of every
attack path with its defence and its test are in
[design/threat-model.md](design/threat-model.md). In short:

- **Memory safety:** Rust everywhere, with `unsafe` kept to a small, size-capped, inventoried core ([design/core.md](design/core.md)). Memory safety is the floor, not the whole answer: logic bugs, races, hardware misuse and DMA mistakes are handled by the measures below.
- **Driver trust tiers:** core, trusted drivers, restricted drivers (all ours, in the kernel), and user-space drivers (anything third party, and anything parsing untrusted input by default), each with its own IOMMU domain and resource budgets, with defined fault containment and restart ([design/drivers.md](design/drivers.md)).
- **Formal verification of the security-critical core:** proofs and bounded checks at stated levels (Kani, Verus, loom) for page tables, the frame allocator, the soundness of the core's safe APIs, process memory isolation, capability derivation and revocation, user-memory copies, resource accounting, the scheduler, the driver boundary, the IOMMU, storage invariants, network packet parsers, the anti-rollback floor state machine, TPM policy composition and the channel graph, with the kernel's cryptography tested against published vectors. The `unsafe` hardware shims are a separate, tested-only target with a size cap. Each target states its assurance level (proved, bounded, model-checked or tested only) and its assumptions, and the level reported is the weakest of its own and every target its assumptions rest on ([design/verification.md](design/verification.md)).
- **Hardware protections:** no-execute pages, write-xor-execute for all kernel memory, SMEP/SMAP, UMIP, guard pages around every stack, KASLR with a position-independent kernel randomised over at least 2^16 slots and measured entropy, page-table isolation where the CPU needs it, page tables in a separate physical zone with guard rows against Rowhammer, and the IOMMU from Phase 1. Control-flow protection: user-space CET shadow stacks from Phase 5; kernel shadow stacks and indirect-branch tracking as soon as the stable Rust toolchain can build for them, in Phase 11 at the latest (tracked on the scorecard until then). Memory encryption (AMD SME, Intel TME) where the CPU has it, from Phase 11 at the latest, with the scorecard showing whether it is on.
- **Least privilege through capabilities:** a process can only touch objects it holds a handle to; Linux file descriptors are capabilities, with a derivation tree and revocation ([design/capabilities.md](design/capabilities.md)).
- **Every app sandboxed by default:** its own view of the filesystem, no access to other apps' data, and access to the camera, microphone, screen, location and user files only through portals whose prompts are drawn by the system (on a dedicated prompt VT reached by Ctrl+Alt+Delete from Phase 5, by the compositor from Phase 7). Apps start with no file, device or network grants: an identity's first non-loopback `connect` or `send`, or its first name lookup at the system resolver, queues one network request. A decision that needs no human is made at once from the level policy, so the call succeeds; when a human is needed the lookup or `connect` waits up to 30 s (`resolv.conf` ships `options timeout:30 attempts:1`), and on refusal or timeout the lookup answers SERVFAIL (`EAI_AGAIN`) and `connect` returns `ENETUNREACH`, never `ECONNREFUSED`. Each request is decided by the user's prompt level, "Always ask", "Only when suspicious" (the default) or "Almost never": it prompts, or is granted silently, logged and revocable in Settings, and the answer is remembered. A closed, tested list says what is suspicious, and a floor always prompts at every level: inbound access, remote control, screen sharing and screenshots, a new HID interface with keyboard, keypad or system-control usages ([design/drivers.md](design/drivers.md) "Device authorization"), any PCIe device or tunnel added after boot on a hotplug port, a desktop launch of a downloaded executable, and data set plus network for one identity or component (the remote-read promise). A component's data set is its persistent file grants plus its camera, microphone, screen capture and screenshot, location, background clipboard-read, USB-portal raw device, `hidraw`, serial and screen-reader (AT-SPI) grants. Network access is a per-identity egress filter that reaches live sockets: a network grant is outbound only, a wildcard socket receives only loopback traffic unless the app holds an inbound grant for that port, and apps whose component has a non-empty data set get no network access unless the user approves that combination. Files from removable media carry the "removable" flag and downloaded files the "downloaded" flag (defined once in [design/capabilities.md](design/capabilities.md) "Provenance"); a desktop launch of a downloaded executable always asks, and the approved program starts as a new identity with no grants, while the terminal running a file it wrote itself never asks.
- **IOMMU on by default from Phase 1:** devices can only reach memory handed to them, interrupt remapping on. From Phase 6 every new USB, Thunderbolt and Bluetooth device, and every PCIe device added after boot on a hotplug port, is held until approved, per USB interface, and while the screen is locked all USB and Thunderbolt ports refuse new devices. Machines without an IOMMU are told so; there, device-read descriptors hold only typed addresses of granted buffers and DMA-address registers are written only by the core, so driver bugs can't aim DMA at kernel data, but a malicious device or radio firmware can, and radios stay off until the user accepts that named exposure.
- **Encryption by default:** Phase 4a encrypts the disk (AES-XTS, confidentiality only); the own filesystem then adds authenticated, per-user encryption with keys evicted on lock ([design/storage.md](design/storage.md)). Keys are sealed to measured boot with a signed TPM policy plus a PIN where there's a TPM, a passphrase where there isn't, and a recovery key is always created. Every sealed TPM object seals only a random value R, and the key material it guards is encrypted under HKDF(R ‖ half of the stretched PIN), so someone who extracts the TPM's secrets still faces a PIN search. Every PIN and passphrase is stretched with Argon2id under one rule (memory min(1 GiB, RAM/4) but at least 64 MiB, at least 4 passes), so an encrypted install needs at least 256 MiB of RAM.
- **Verified and measured boot:** firmware checks the bootloader, the bootloader checks a signed config that pins the kernel and the system image's hash tree root, and every step is measured into the TPM. Anti-rollback, A/B slots, boot counting and a recovery image are in [design/boot.md](design/boot.md).
- **Nothing listening by default:** no remote-access services, a default-deny inbound firewall.
- **Lockdown:** no interface lets anyone, root included, load unsigned ring-0 code or read kernel memory ([design/threat-model.md](design/threat-model.md)).
- **Signed updates only,** with a TUF-style key hierarchy, an offline root, a transparency log whose checkpoints are cosigned by at least 4 independent witnesses at threshold 2, reproducible builds and anti-rollback; the update client ships in Phase 7, so the minimum product can be patched.
- **CPU side-channel mitigations** chosen per CPU model after microcode is loaded, including Spectre v1 index masking in safe Rust parsers; GDS is mitigated by microcode or by turning AVX off through XCR0; SMT is off by default on CPUs affected by MDS, L1TF, TAA or RFDS, and core scheduling is an opt-in for app-to-app isolation only (on by default only where siblings can't leak kernel data); costs benchmarked and published.
- **Testing security like everything else:** every attack path in the threat model has a test that becomes a gate in the phase it lands; continuous syscall, network, device-side and filesystem fuzzing; outside audits of the core at the end of Phases 1, 3, 4a and 4b and before 1.0.

## How we know it is good

- **CI on every change:** build, `rustfmt`, `clippy` with warnings as errors, the in-kernel tests and a boot matrix in QEMU: 64 virtual PCs (BIOS and UEFI, old and new chipsets, 128 MiB to 8 GiB of RAM, 1 to 16 cores), each booted 3 times. Lands in Phase 1: Limine and every other download pinned by SHA-256 and GitHub Actions by commit hash, the core's lint rules, the unsafe inventory and core size check, `cargo-deny` and `cargo-vet`, and the gate-table check below. Lands in Phase 1a: the exact Rust toolchain pin (a version, not a channel name) in `kernel/rust-toolchain.toml` and `bootloader/rust-toolchain.toml`, with a CI check that rejects a channel name in any `rust-toolchain.toml`, and the proofs job, with Miri on the host tests of every pure tier-0 crate. loom lands in Phase 1c (single-CPU interrupt re-entry and the page-table walker thread) and shuttle in Phase 2.
- **Gate tables match the plan** (lands in Phase 1): a CI script checks that every proof target and level change in [design/verification.md](design/verification.md), every attack row in [design/threat-model.md](design/threat-model.md) and every compatibility milestone's suite and target in [design/compat.md](design/compat.md) is named in the done-when of the phase its table gives, that no done-when below names a gate those tables put in another phase, and that every proof level is written own/effective.
- **No silent skips.** A test that can't run (missing firmware, missing tool) fails CI unless it is on a checked-in allowlist with a reason. A green run means everything listed actually ran. Compatibility pass rates use one skip rule, the same as [design/compat.md](design/compat.md): every skipped test counts as a failure, and a test on the phase's excused list is shown separately and still counts against the rate.
- **Nightly soak:** the same matrix booted 40 times per configuration (over 2,500 boots) to catch rare, timing-dependent bugs. Soak tests grow with every phase: hour-long scheduler stress, file system crash-state runs, driver kill-and-restart loops, continuous fuzzing.
- **In-kernel test suite** (from Phase 1): unit tests that run inside the kernel under QEMU, so allocators, page tables and the scheduler are tested in the real environment.
- **Tough but realistic conditions** (from Phase 1): every change also boots on deliberately awkward machines: CPUs from Core 2 to current Xeon/EPYC with security features missing, 5-level paging, odd core topologies, NUMA (including a node with no memory), odd and split memory, no HPET, no ACPI, old and new OVMF builds, a host fighting for CPU, and Secure Boot attacks (unsigned bootloader, wrong key, tampered kernel, tampered config, old signed image), which must be refused. Fault injection joins as each piece lands: failed allocations, quirky ACPI tables, timer jitter, spurious interrupts, hostile DMA devices, then disk power cuts and I/O errors.
- **Public scorecard from the first bootable build:** performance against a pinned, matched Linux baseline (booted with the same SMT setting, `nosmt` on affected CPUs), measured on dedicated bare-metal machines driven by a separate controller host (shared CI VMs are too noisy and are used for functional tests only), with the latency tracer off in every benchmark boot and its enforcing stress boots in their own slot (1 hour a day on the gate machine). Non-tail metrics get at least 3 runs in each of at least 20 boots per build. Tail metrics (P99 and above, variances) pool their events per boot, treat the boot as the cluster and need at least 20 boots per kernel, gathered in rolling windows (the nightly block judges the last 5 nights, the extended microbenchmark block the last 4). Each night also runs a change-point test: the newest 20 candidate boots against the 20 before them (for the extended block's tails these span 8 nights); a window failure or a change-point hit is bisected by binary search over the window's builds, at most 3 steps, each comparing 20 boots of the middle build against 20 of the last passing build, from a named bisection budget, and once the offending change is reverted its builds' boots leave the window. The per-change microbenchmark tier runs after merge, per merge batch: a failing batch is bisected and the offending change reverted automatically within 24 h (the whole batch, re-queued one change at a time, if bisection can't finish), so "nothing merges unless" means the CI tests, and the per-change benchmark gate acts by revert. A/A runs each release cycle (the candidate identical to the base, matched LTS against itself, the change-point test included) publish each gate's false-fail count and each metric's false-fail rate; the harness has failed only when the one-sided 95% lower bound of a metric's pooled 12-cycle false-fail rate exceeds the rule's design rate, or a cycle's false-fail count exceeds the 99th percentile of Binomial(k, design rate), and a harness failure holds the next scorecard release. Every machine is scheduled under 168 hours a week, and a scorecard release comes at most once per 4-week release cycle. The release rule compares each release with the last one over k = 150 tracked metrics at most: a metric fails when a one-sided Holm test at family-wise 5% over the k shows it worse and its estimate is beyond its margin (3% for a non-tail metric, 0.5% for the geometric mean of the desktop set's non-tail metrics, 5% for a P99, 8% for a P99.9), and the failure stands only after a confirmatory rerun on 20 fresh boots per build. Every phase gate uses one decision rule: an absolute target is met when the one-sided 95% bound on the worse side meets it; a comparative gate (against Linux, the last release or another Optimal path) is met when the worse end of the Holm-corrected two-sided 95% confidence interval meets it, over at least 20 boots per kernel, against both matched LTS and matched stable Linux; and "no worse than matched Linux" is judged by the same form over the gate's j comparisons with a threshold of 1.02 on Optimal/Linux, published as "not shown worse than 2%". No margin grows with the standard error: a metric short of its SE target gets more boots, or is published as "below target power" and judged at the same margin. Benchmarked kernels are built with 64-byte alignment of hot functions and loops and the 32-byte branch-boundary option (the JCC erratum). Committed provisional targets can only tighten, and a security scorecard per hardware tier counts only what is on in the shipped image. See [design/benchmarks.md](design/benchmarks.md).
- **Formal verification in CI:** every proof target runs on every change, with up to 20% of each target's harnesses run nightly instead, with time budgets and tracked bounds ([design/verification.md](design/verification.md)).
- **Fuzzing:** syscalls from Phase 3, the driver boundary, device-side driver fuzzing, the boot keyboard readers, filesystems and the pre-cap Optimal header block parser from Phase 4a, each user-space trusted service's protocol (10^8 executions) from the phase it lands in (5 to 7), the network stack, Wi-Fi, Bluetooth, USB descriptors and the udev-compatible daemon from Phase 6.
- **What runs today and what lands later.** Each item above is marked on the scorecard as running now or "lands in Phase N"; nothing is described as running before its job exists.
- **Real hardware:** from Phase 1, each milestone is also checked on at least one real PC booted from USB.

## Phases

Each phase ends with a "done when" test, and every item listed in a phase is
part of that test: if a phase builds something, its done-when checks it. Work
that depends on a phase doesn't ship until that phase's done-when passes.
Work that doesn't depend on it (the built-by-us tracks, proofs, fuzzing,
security items) runs in parallel and is never held back by a later, unrelated
phase. In particular, no security item waits for GPUs or games.
Phase 1 has lettered parts (1a to 1d). Storage and the trusted boot chain
are two lettered phases, 4a (storage) and 4b (trusted boot chain), and
every item of that work names its phase, never both at once.
The file system track starts after 4a.
Each done-when ends by naming the proof targets and their levels, always
written own/effective (for example "P/T" or "T/T")
([design/verification.md](design/verification.md)) and the attack rows
([design/threat-model.md](design/threat-model.md)) that gate in that phase.

### Phase 0: It boots (done in CI)
- Rust kernel loaded by Limine, writes to the serial port, paints the screen and reports usable memory.
- CI builds the kernel, makes a bootable ISO, boots it in QEMU on BIOS and UEFI, and uploads the ISO.
- Done when: CI is green and the ISO boots on a real PC from a USB stick, showing the blue screen band.

### Phase 1: The core
- **1a, CPU setup:** GDT, TSS, IDT, and handlers for every CPU exception with a clear crash report (registers and a stack trace); a double-fault handler on its own IST stack so stack overflows are reported; the proofs CI job and Miri land; the exact toolchain pin in `kernel/` and `bootloader/`; the bootloader workspace falls under the core's rules from here (its tier-0 crates capped at 3,000 lines, of which shim code is at most 1,500, [design/core.md](design/core.md)).
- **1b, memory:** physical frame allocator (NUMA-aware), our own page tables for the kernel, a fallible kernel heap, guard pages; the memory-access backend (phys-to-virt and entry accessors behind a trait the pure crates are generic over, about 150 lines in `core-mm`, with its shim contract and CI check); the kernel built position-independent, picking its own virtual base over at least 2^16 slots at 2 MiB granularity, and its direct-map base, when it builds its own page tables (KASLR, the same under Limine and Optimal Boot); its physical load address is chosen by the loader, and under Limine the scorecard reports physical KASLR as "not done until Optimal Boot"; page-table and IOMMU entries are `PAtomicU64` of the vendored `vstd` subset from here; the first proofs of memory targets.
- **1c, ACPI, interrupts, IOMMU and time:** ACPI tables, AML hosting staged as in [design/drivers.md](design/drivers.md) (safe Rust, fuzzed, confined; a SystemMemory access that overlaps any ECAM range goes through the same PCI config filter as a PCI_Config access, which refuses writes, on every function assigned or not, to the BARs and ROM BAR, the command register's Bus Master Enable and Memory and I/O decode bits (other command bits pass, for `_OFF` methods), a type-1 header's bus numbers and memory and I/O windows, MSI and MSI-X, ACS, Device Control (phantom functions) and Device Control 2, the ATS, PRI, PASID and SR-IOV capabilities, the ACS-quirk vendor registers, the host bridge's VTBAR and the AMD IOMMU capability base), minimal PCI enumeration (enough to find and program the IOMMU), local APIC and I/O APIC, the IOMMU in deny-all mode (every unused Intel context entry and all 65,536 AMD-Vi device table entries per segment blocking DMA and interrupts; Intel in scalable mode when ECAP.SMTS is set and translation is off at hand-off, else the inherited or legacy mode; AMD rewriting inherited device-table entries in place; every multi-word VT-d context or PASID entry written with its present bit cleared first and set last, and every live AMD-Vi device table entry rewritten through blocking intermediates (each 128-bit half with `cmpxchg16b`, never V=0 on a live device), and on VT-d with `ECAP.C`=0 every written table line flushed with `clflush` before the invalidation is queued) with interrupt remapping (every IRTE with SVT=01 and the exact requester ID, except SVT=10 with the bridge's bus range for a device behind a PCIe-to-PCI bridge), requester-ID aliases (bridges, DMAR and IVRS aliases, phantom functions, the quirk table) sharing the device's domain and group, the viable-group rule (a domain never mixes a tier-3 device with a tier-1 or tier-2 device), and bus mastering cleared on every bridge and root port and then every function in the defined order ([design/drivers.md](design/drivers.md)), kept off until assigned. DMA is stopped by the bridge or root-port Bus Master Enable plus the IOMMU, never by a device's own BME. Exempt: the IOMMU's own function, the firmware display and the bridges on its path, and USB host controllers still owned by the firmware and the bridges on their paths, which stay with the firmware (BME on, in a domain holding only their RMRRs) until the Optimal driver that runs them starts. On D2 machines only, BME stays clear on every external port (one with the ACPI `ExternalFacingPort` property, in a Thunderbolt or USB4 topology, or named by a DMAR SATC entry, never a port with only the Hot-Plug Capable bit); below a hotplug-capable port that isn't external, devices present at boot may master and devices added after boot are refused. Boot-services and bootloader-reclaimable memory is not reused until bus mastering is cleared and the IOMMU is live. A machine with no firmware pre-boot DMA protection shows the named "boot DMA window" exposure. Time: a TSC invariance check, calibration from CPUID leaves 15h/16h, else HPET or the ACPI PM timer, else the PIT, and a clocksource watchdog; timer events from the LAPIC TSC-deadline mode, falling back to LAPIC one-shot, HPET, then PIT; the clock-drift exchange on the 16550 UART. Microcode loaded on the boot CPU before mitigations are chosen. loom starts with the single-CPU interrupt re-entry models and the page-table walker thread. A test-only in-kernel DMA driver for an edu-style QEMU device (`DmaBuffer`, `IrqHandle`), built only in test images, carries the 1c tests that need a device the kernel drives.
- **1d, console:** a framebuffer text console so the kernel can talk without serial (with a font we make or that is permissively licensed).
- The kernel becomes a workspace with tier-0 crates and enforced lint rules, the unsafe inventory and the core size cap ([design/core.md](design/core.md)).
- Security baseline: no-execute, write-xor-execute kernel mappings, SMEP, SMAP, UMIP, guard pages, KASLR. The shipped image moves to the hash-pinned, enrolled Limine chain (not done yet: the current ISO ships stock, unsigned Limine and enrols nothing), keeping the BIOS image for B4, with a CI check that fails the release build unless the ISO's `limine.conf` hash is enrolled in its Limine binary. Supply chain: the exact toolchain version, Limine's SHA-256 and every other build input pinned.
- In-kernel test runner in CI, plus the tough-conditions run and Secure Boot attack tests. The "old signed image refused" test puts the old image's hash in dbx in the test OVMF variable store, because Limine has no security version number.
- The hostile-device emulator: our own vfio-user device server (permissively licensed, built on libvfio-user), attached to an unmodified QEMU at a pinned version used as an external test tool.
- First scorecard entries: boot time, timer accuracy, kernel memory, and the security table.
- Where it runs today: CI covers QEMU boots, the in-kernel tests and proofs as each lands; real-hardware and bare-metal items are reported "not yet measured" until the owner's machines are online.
- Done when: every exception type is triggered on purpose in tests and reported correctly; the allocator and page tables pass their tests; every tough-conditions scenario passes; the KASLR tests in [design/boot.md](design/boot.md) pass (an SP 800-90B estimate of at least 9 bits for the picker's output over 10^6 host draws, a 90B estimate for each raw source: EFI_RNG, RDRAND/RDSEED and the TSC fallback; and at least 95 distinct bases in 100 QEMU boots); boot time from firmware handoff to kernel ready is under 300 ms on the reference desktop (mean over 20 boots, one-sided 95% bound); the timer drifts under 1 part per million over a 10-minute run on the dedicated KVM host, with QEMU's CPUID level at least 0x15 and an explicit `tsc-frequency` read by the guest from CPUID 15h, measured as the least-squares slope of the kernel's once-a-second clock lines on the 16550 UART (polled, no DMA) against their arrival times taken on the host with `CLOCK_MONOTONIC_RAW` (never against the calibration source, and never on hosted runners, whose clock is itself a guest clock; the bare-metal drift test is in Phase 2); the Secure Boot attack tests refuse an unsigned bootloader, a wrong key, a tampered kernel, a tampered config and an old signed image (through its dbx hash entry); the release build's enrolment check runs; QEMU `usb-ehci` and `piix-uhci` controllers, and a `qemu-xhci` behind a `pcie-root-port`, stay with the firmware, BME on along their path, in a domain holding only their RMRRs; Optimal Boot measures its own security version number, then the config-signing key ID, into PCR 8. The PIN is stretched under the KDF rule of Phase 4a and mixed into the key; on firmware-TPM machines a passphrase of at least 60 estimated bits is required instead. Optimal Boot reads the PIN through UEFI `ConIn` before `ExitBootServices`, above an anti-phishing TOTP code (RFC 6238) from a sealed HMAC key that the user checks against their phone; the TOTP key is bound to the signed PCR 4, 8 and 9 policy, the floor and PCR 7 through a `PolicyOR` over its accepted values (resealed on OS-applied changes), so a boot with Secure Boot off or with PCR 7 changed outside Optimal shows no code, the kernel records the RTC-to-UTC offset at shutdown, and a re-enrolment flow covers a boot that shows no code. The loader warns when the PCR 7 log shows Secure Boot off or PK, KEK or db changed (without a firmware setup password a correct code doesn't prove the firmware unchanged, a residual on the scorecard). Dictionary-attack lockout: 32 tries, recovery time 7,200 s, lockout recovery 86,400 s; `TPM2_Shutdown(CLEAR)` on every reboot, power-off and panic path and `TPM2_Shutdown(STATE)` at suspend; the kernel resets the lockout counter before capping after every good disk-secret unseal, with the lockout secret it holds wrapped under the service-key secret. On a TPM another OS already provisioned (Windows in a dual boot) Optimal never changes an authorisation it doesn't hold: without the lockout authorisation there is no lockout reset and the budget is the TPM's existing maxTries and recoveryTime, shown at install; without the owner authorisation the only way on is a TPM clear the installer explains first.
- Optimal Boot accepts only configs signed (Ed25519) by the config-signing key: offline, held 2-of-3 on hardware tokens as a delegated TUF role, its public half built into the loader, revoked by a loader with a higher SVN, and rotated in a fixed order (configs dual-signed in the other slot and both recovery copies, then the loader update, then the floor raise). Each config carries a transparency-log inclusion proof and a checkpoint cosigned by the witness set built into the loader (at least 4 witnesses, threshold 2, changed by a signed loader update or, in an emergency, by a witness-set change signed by the offline root, 2 of 3, and cosigned by at least 1 old witness or published in the log for 30 days with a trusted-path notice; each witness set has a monotonic version kept with rollback protection under the floor). The loader installs deny-all IOMMU tables before anything else (the TPM's CRB or TIS interface needs no DMA); the exceptions are the RMRRs, the firmware framebuffer (read-only) and, while firmware drivers need them, the boot disk controller and the console keyboard controller, the keyboard controller only if it is not below an external-facing port. Where firmware offers `EDKII_IOMMU_PROTOCOL` the loader installs its own implementation, which maps only the buffers drivers `Map()`; otherwise each exception maps RAM only, minus the loader image and one excluded pool from which every other loader page is allocated (the IOMMU tables, the loader's stack, heap and page tables, the hand-off pages, the kernel's destination and the PIN and secret pages). The order is fixed: every disk read the boot needs (images and the header block) is done; the boot disk controller's exception is removed and the IOTLB invalidated; the images are checked and measured in the pool; only then is object 3 unsealed, the PIN read and the remaining firmware I/O done. It then calls `ExitBootServices`, drops the keyboard exception, and re-checks the IOMMU and re-arms it if a firmware handler turned it off, before handing over. It builds its tables in the kernel's translation mode with the kernel's pure IOMMU-table crate, and where it can't program translation it uses PMRs, which count only if they cover every page the kernel and loader occupy; a USB or PCIe `ConIn` keyboard without `EDKII_IOMMU_PROTOCOL`, a PMR-only boot that reads the PIN, and a boot with no usable IOMMU (D2) show the named "pre-loader secret DMA window (keyboard path)" on the scorecard. D1 requires the firmware's pre-boot DMA protection; without it the loader's tables alone show the named "pre-loader DMA write window". It disables the platform hierarchy if the firmware left it open.
- Sealing happens at the first boot from disk, never in the installer: the installer sets the TPM's owner and lockout authorisation, creates the SRK, and writes the Optimal header block (format from Phase 4a) with the volume key wrapped under the passphrase and the recovery key and the volume tags. The first boot unwraps the volume key from the header block with the recovery key (no boot path reads a LUKS2 key slot, and first-boot sealing writes none), checks the volume tags and caps; a volume installed in Phase 4a seals the same way at its first 4b boot; after capping it replays its own PCR 4 and PCR 7 log, picks the PCR 4 variant and works in this order: the service key and the mark key; then, with the owner secret the recovery key unwraps, it defines, increments or writes, and locks every NV index (the anti-rollback counter and its base, the storage replay counter and its base, the PIN-epoch index, the TOTP time index and F2's 8 per-user indexes of 32 bytes, fewer down to 0 on a TPM without room, with the counts on the reference fTPMs published); it reads back their values and names; only then it creates objects 1 to 3 and the lock-screen PIN object. Each new object is checked by comparing a trial-session policy digest with its authPolicy, because a real test-unseal can't run after capping; the second boot unseals with the PIN alone before capping, which is the real test.
- The Optimal header block is the only part of the data volume read before capping: the last 16 KiB before the LUKS2 data offset, which is fixed at 16 MiB, in two 8 KiB copies, each starting with a magic that names the stage, then a version and a CRC-32C, holding the KDF parameters, the SRK and base-index names, for each LUKS2 key slot Optimal writes (passphrase, recovery) its KDF parameters and a write generation, the volume tags and 15 fixed 512-byte slots (the sealed blobs, the volume key wrapped for each way Optimal opens it, the encrypted S, S wrapped under the recovery key, the owner and lockout secrets, and in slot 15 the panic-hibernate key of Phase 10). Each LUKS2 header copy has its own volume tag, HMAC-SHA-256 keyed from the volume key over that copy (binary header and JSON area) and the header block's fields other than the tags and the slots; each header-block copy holds a current and a pending tag set, written pending, flush, both LUKS2 copies, flush, promote, flush, and either set is accepted. The tags are checked before S is unsealed and before any JSON is parsed; the kernel uses the primary LUKS2 copy if its own tag verifies and its JSON passes the allow-list, else the secondary, never choosing one by seqid. Optimal's LUKS2 JSON is deterministic (salts = HKDF(volume key, slot index ‖ generation)), so a recovery-key boot that finds no verifying tag (after `cryptsetup luksAddKey` from Linux, say) regenerates it, shows the JSON diff, checks the allow-list, asks on the trusted path, re-tags after capping with S and every sealed secret never unsealed, then reboots. Only one operation that writes the other header-block copy is pending at a time: a PIN change waits for a pending floor raise or PCR 7 reseal, and a raise or reseal waits for a PIN change. Its parser, the kernel's and the loader's (built and fuzzed from Phase 4a), is proof target 15's pre-cap part, together with the PIN-epoch index's read authorisation, fuzzed to the in-kernel thresholds with both stage magics and unknown ones in the corpus.
- PCRs 8 and 9 are capped unconditionally, with a fresh random 256-bit boot nonce extended into PCR 9 so capped values differ on every boot, whatever the unseal result (passphrase fallback included), before any byte of the data volume beyond the Optimal header block is parsed; the LUKS2 JSON and the volume map are parsed only after capping. Sealed objects 1 to 3 are the list every floor raise and every predicted PCR 7 reseal covers: the disk secret, the service-key secret S and the anti-phishing TOTP key with its mark secret; objects 4 (the hibernation key) and 5 (the resume object) come in Phase 10. Every object with the PIN step seals only a random 256-bit R, and the key material it guards is encrypted (XChaCha20-Poly1305) under HKDF(R ‖ second half of the stretched PIN) and stored in the header block, so the TPM never releases key material. S carries `TPM2_PolicyAuthValue` (the stretched PIN) and is unsealed only after a volume tag matches. Objects 1 and 2 also carry `TPM2_PolicyNV` (EQ) on a PIN-epoch NV index raised at each PIN change, so a restored pre-change header copy opens nothing with the old PIN; a recovery-key rotation re-wraps the volume key, and an optional online re-encryption changes the volume key itself ([design/storage.md](design/storage.md)). The full policy composition of every sealed object and NV index is proof target 17. The secrets the kernel holds after capping (each R, the TOTP key and mark secret, both stretched-PIN halves) are kept encrypted under HKDF(S, `optimal-held`). Objects used after capping (per-user home keys, the storage replay counter, the PIN-epoch index, F2's 8 per-user NV indexes and the lock-screen PIN object) carry `TPM2_PolicySecret` against the service key, so only a kernel that passed the pre-cap check can use them. The lock-screen PIN object (DA-protected, with that `PolicySecret`, `TPM2_PolicyAuthValue` on the PIN's stretched authorisation half and `TPM2_PolicyNV` on the PIN-epoch index) is created at first-boot sealing and checked from the 4b kernel console; after exactly 10 failures the lock screen accepts only the passphrase.
- Anti-rollback: the floor is the NV counter's value minus a base kept in a write-once NV index, both defined at the first boot from disk, and the counter's authPolicy uses `TPM2_PolicyAuthorize`, so the disk policy key can rotate. Raising it takes two boots: after the health check (local checks only), user space writes the other slot and both copies of the recovery image at the new SVN, verifies their contents, and writes a "commit SVN n" request into loader state, and on B1 the kernel, while still up, reseals objects 1 to 3 at the new floor, checks each new object's authPolicy against a trial-session policy digest and writes the set into the other header-block copy. On the next boot the loader checks the other configs' signatures and SVNs and hands the result over; on B1 the kernel really unseals each new object before capping and only then raises the floor (increments the counter), and on B2 the loader raises it; a boot that resumes from hibernation leaves the request pending. Each loader has a built-in minimum config SVN lagging one security release, and a loader is installed only after a completed floor raise at or above that minimum. Every predicted PCR 7 reseal (dbx, db, firmware, shim or SbatLevel) reseals objects 1 to 3 the same way. On B2 machines (no TPM) the floor is a boot-services-only UEFI variable; if it is missing or corrupt the floor is max(the minimum config SVN built into the loader, the highest SVN among the configs on the ESP), and the scorecard says B2 anti-rollback holds against OS-level attackers only (against physical ones only with owner keys).
- TPM clear detection: the SRK name and the base-index name are recorded in loader state and the header block; whenever the anti-rollback counter and its base exist, the floor is max(the loader's built-in minimum, the highest SVN among the configs on the ESP, counter − base), and a recorded name that differs is reported as tampering but changes nothing. The TPM counts as cleared only when the SRK, the counter or the base is missing: the floor is then max(the built-in minimum, the highest SVN present), the loader warns and shows no code, and older loaders stay retired through SBAT and dbx, which survive a clear. A recovery boot never redefines a counter that exists, except at a PCR 4 variant change, which keeps the floor read before capping. The storage replay counter has its own write-once base index (replay value = counter − base); the replay counter, its base, F2's NV pool and every home-volume TPM wrap are on the list every reseal and every clear recovery covers, and after a clear the user sees the volume's last authenticated commit time and generation on the trusted path before accepting; a home then opens from its passphrase slot alone and its TPM part is resealed at the next login.
- Two loader directories, each with its own `Boot####` entry, plus the `\EFI\BOOT\BOOTX64.EFI` fallback: an update writes the inactive directory, verifies it and trial-boots it with `BootNext` (its own tries counter, at most 3 trials), and `BootOrder` moves to it only after user space marks it good; an SBAT or dbx revocation is applied only after both directories and the fallback carry the new generation. A failed loader-state write boots the current slot, reports, and stages nothing. Slots are found by partition type GUID on the boot disk, and the recovery image's PCR 8 and 9 approvals are signed so it shows the code. Shim revocation from outside is tracked: Optimal follows upstream SBAT and dbx and ships a new shim before the old one is revoked, and the documented way back is Secure Boot off (a B3 boot), reinstalling the loader and a recovery-key reseal.
- The 4b stand-ins ([design/boot.md](design/boot.md) "Tests"): a pre-desktop kernel console is the 4b trusted path (the prompt VT grows from it in Phase 5), from which credential changes, the re-tag, the confirmation after a clear, re-enrolment and the lock-screen PIN object's check run; a signed test health agent marks a slot or loader good; and a minimal signed slot/loader stager does `BootNext` re-arming, the `BootOrder` flip, floor-raise stage 1 and config-key rotation step 1. The tests that use the stager or the health agent rerun with the update client in Phase 7.
- Optional features ([design/features.md](design/features.md)): the tamper alert (F7, on by default): an S-authenticated record of each good boot's event log for PCRs 0 to 5, 7, 8 and 9, compared at the next boot and listed in plain English after unlock, with Optimal's own changes marked expected.

### Phase 5: Running real Linux programs
- Before this phase starts, the desktop benchmark set is frozen and versioned, and the reference desktop's discrete GPU model is fixed and recorded, so the locked machine state doesn't change afterwards.
- Compatibility milestones 2 to 7 in [design/compat.md](design/compat.md) (2 and 3 start in Phase 3 and 4 in Phase 4a; all gate here): dynamic linking, threads, PI futexes and `futex_waitv`, `/proc` and `/sys` per the contract, desktop IPC, a loopback-only TCP and UDP stack (`AF_INET` and `AF_INET6` on `127.0.0.0/8` and `::1`) with the per-identity loopback rule, namespaces, seccomp and cgroups, the FUSE protocol, rootless podman with `--network=none` and with a loopback-only network namespace (milestone 6), `ptrace` and `perf_event_open`, and `modify_ldt` with an espfix64-style per-CPU read-only alias stack, so an `IRET` to a 16-bit stack segment leaks no kernel stack bits (milestone 3; the Phase 5 Wine first-run test needs it). Network drivers, the full stack, `/dev/net/tun`, podman with pasta or slirp4netns networking and the LTP net tests come in Phase 6 (milestone 8). Each phase's pinned test list and excused list are frozen when the phase starts; removing a test or adding an excuse needs the owner's sign-off. LTP runs with an owner-signed classification file (every pinned test is security, divergent or normal) and owner-signed expectation files, and with `/dev/loop-control` and `/dev/loop*` backed by the tier-3 file system server.
- Scheduling ABI (policies, affinity, cgroup CPU control, the `sched_attr.sched_runtime` slice), pressure information, compressed swap, transparent huge pages and INVLPGB broadcast shootdowns, user-space shadow stacks, io_uring (milestone 5).
- The permission broker and portals, with prompts on a dedicated prompt VT reached by the secure-attention key (Ctrl+Alt+Delete) until the compositor can draw them in Phase 7 ([design/capabilities.md](design/capabilities.md)); the secure-attention key and prompt answers are accepted only from the in-kernel keyboard parsers. The prompt level ("Always ask", "Only when suspicious", the default, or "Almost never") is a TCB setting the broker stores and only the trusted path changes; below the chosen level a grant is given silently, logged and revocable in Settings, and the floor (inbound access, remote control, screen sharing and screenshots, a new keyboard, keypad or system-control HID interface, a PCIe device or tunnel added after boot, a desktop launch of a downloaded executable, data set plus network for one identity or component) prompts at every level. The default profile has no network: an identity's first non-loopback `connect` or `send`, or its first lookup at the resolver, queues one network-portal request, decided by the prompt level and remembered; a silent decision is made at once from the level policy the broker pushes into the kernel and the resolver, so no app sees a failure when no human is needed, and when one is the call waits up to 30 s (an `O_NONBLOCK` connect returns `EINPROGRESS`; a first-use `sendto` blocks, or returns `EAGAIN` with `O_NONBLOCK`), then a refused or timed-out lookup answers SERVFAIL (`EAI_AGAIN`) and `connect` returns `ENETUNREACH`, never `ECONNREFUSED`. The system resolver, a TCB service at `127.0.0.53`, lands here (`resolv.conf` ships `options timeout:30 attempts:1`; it dedupes retransmits per identity and answers SERVFAIL within 5 s on an upstream failure, and the kernel stamps the sender identity on loopback datagrams and TCP connections to it), forwarding to a fake upstream on the loopback-only stack until Phase 6. Until the settings app (Phase 12), "Settings" is a trusted-path settings console on the prompt VT (in the compositor from Phase 7, [design/capabilities.md](design/capabilities.md) "Settings before Phase 12"); Phase 5 ships its prompt-level, silent-grant log and revocation, document and folder grant screens and F4's options. Before Phase 6 the prompt terminal and the secure-attention key accept USB input only from the port and device that typed the unlock secret this boot (the device behind the EFI `ConIn` path the loader records and hands over; if no path is known, the kernel's reader asks for a typed code after hand-over). setuid replaced by brokers. D-Bus proxies and per-app keyrings are mediated from here. The SSH agent, GPG agent and secret service are our own TCB services (budgets of 4,000, 8,000 and 6,000 lines) whose prompts go through the broker. The lock screen runs on the prompt VT (in the compositor from Phase 7) and fails closed. Every trusted service that sends traffic for an app (open-URI here; the notification and email portals in Phase 6) checks the caller's grants: open-URI with a non-file scheme from an identity without outbound network shows a prompt naming both apps and the full URL. Autostart goes through the Background portal, shared settings through the settings portal, and the Flatpak portal (`org.freedesktop.portal.Flatpak` `Spawn` and `SpawnSignal`) starts child identities with a subset of the caller's grants. Kernel crash dumps leave out slab caches tagged as carrying user data (keyring payloads, pipe and socket buffers, tty buffers, dentry names).
- App identity: grants, the closure record and the private home are keyed by an identity ID, never a path: (ID, publisher or remote signing key) for a manifest or Flatpak app, and (launch path, a random 128-bit lineage ID created at first launch, argv hash) for an unpackaged program, whose launch closure (an interpreter plus the script's hash, the full argv for `-c` style calls and every file the interpreter opens from the script's own tree or the listed site-packages and classpath roots; an ELF program's `PT_INTERP` and every library it maps from outside the system image; an AppImage file) is recorded at first launch. The lineage carries to a new closure hash only across an update whose changed files the app itself, its declared parent or (after a prompt) the terminal wrote; any other writer gets a new lineage with no grants and an empty home, and the old home is retired to `~/.var/app/.retired/`. A changed signing key is a new identity. The install directory of every desktop-launched program is protected against other app identities only: it stays visible and writable to the terminal identity, and a directory whose files all have terminal provenance is never protected. The protected launch paths include `~/.local/share/dbus-1/services`, `~/.config/systemd/user`, `~/.config/environment.d`, `~/.config/mimeapps.list` and autostart, and the service manager and D-Bus activation apply provenance. Files carry kernel-set provenance (the writing identity and a write time never earlier than the signed time floor), plus the "downloaded" flag, defined once in [design/capabilities.md](design/capabilities.md) "Provenance" (written into a download folder, arriving through a portal from a networked identity, or written by a process that has read from a non-loopback socket since its last `execve`, a taint that spreads across pipes, Unix sockets, shared memory and `fork` within an identity and is identity-wide for a non-terminal app identity), and the "removable" flag from removable or foreign volumes; tags are kept by kernel copies and by the terminal's low-water mark, and files an identity writes inside its own install directory or closure keep its provenance. A desktop launch of a downloaded executable is in the floor, and one with another app's provenance or the removable flag follows the levels; approved, it runs as a new identity in the default profile. A terminal-identity process that executes a file of another identity's provenance or the removable flag, or opens a code-bearing file of that provenance (`Makefile`, `.envrc`, `.git/hooks`, `.git/config`, npm scripts), follows the levels and gets `EACCES` where the level asks, until the user approves it; the terminal executing a file with terminal provenance is the user's own typed action and never asks. A registered app run from a shell starts through the launch relay under its own identity, with its argv, the typed environment minus a denylist (`LD_*`, `*PRELOAD`, `PYTHONPATH` and similar), the cwd, and the caller's rlimits, nice value, CPU affinity and cgroup passed (when the `execve`ing process is traced, the app starts stopped and the tracer gets a debug capability through the debugger portal), and path arguments and the cwd turned into one-use document-portal entries (the user's own typed action, no prompt); the stdio relay from a typed command line is the user's action for that run, an edge that lasts the process lifetime and joins no components. Only the launcher and the service manager hold the capability to spawn a process with an identity, and children get at most their parent's grants.
- The terminal: `TIOCSTI` returns `EPERM`, `TIOCLINUX` is absent, the launcher gives a fresh pty whenever it starts a different identity, terminals ignore OSC 52 and report sequences from foreign identities, and a writable grant inside the terminal's home doesn't join the app to the terminal; its prompt says the terminal will ask before running anything the app writes there.
- Direct channels: every channel in the closed list `design/channels.toml` (cross-identity loopback connections included; the OAuth loopback auto-grant applies only if the requester already holds network) is directional, and the kernel keeps a per-session directed graph of them, a pure crate (proof target 18), dropped at logout, with grant-created edges rebuilt at login. An identity's component is itself plus every identity with a path to it, and the data set plus network rule applies to components: it is checked when a channel opens and at every new grant (network, folder, sensor, inbound port, persistent document), a combined approval names each source in the component's data set and its networked members and is asked again when either grows, and a refused combination refuses the grant at grant time with the reason. A refused channel open queues one combined-approval request per identity pair and returns `ECONNREFUSED` or `AccessDenied` at once; a retry after approval succeeds. ### Phase 8: Real GPU drivers
- The hardest part of any new kernel. Start with one family (AMD or Intel) and work towards accelerated 3D through Mesa, split into a small, size-capped tier-1 GPU core, display and power code in the tier-2 framework, and tier-3 management, under the written clean-room process ([design/drivers.md](design/drivers.md)). The driver targets the reference desktop's discrete GPU, the model fixed before Phase 5. Every GPU page-table entry is built only from a `DmaBuffer`, `Iova` or `VramBuffer` handle (a VRAM range the kernel allocated to that buffer object and cleared), on D1 and D2 machines alike. VRAM and GTT buffer objects are cleared by the GPU's copy or clear engine before their first mapping, with the cost benchmarked and on the scorecard. Display surface, cursor and LUT address registers and the SMU messages that pass a DRAM address are core-only operations. A fault in the tier-2 display part stops only that sub-function (its accessor and core-only operations revoked, display init re-run without FLR), escalating to an adapter reset only if that fails. The GPU's own firmware (GuC, MES, PSP, SMU) is listed in the trusted base and the firmware ledger. Compatibility milestone 11.
- Optional features ([design/features.md](design/features.md)): the game mode overlay (F8, off by default): frame time, P99 and P99.9, estimated input latency and top CPU users, drawn by the compositor on its own hardware plane.
- Done when: Mesa runs hardware-accelerated OpenGL and Vulkan on one GPU family; the milestone 11 suite (Mesa's tests, piglit, the pinned Vulkan Conformance Test Suite subset and the IGT subset) reaches 90% on each, and 100% of its security-class tests; the cross-process GPU buffer isolation test passes; a canary written into VRAM and GTT buffers and freed (including through a context kill and an adapter reset) is never read back by another process through the GPU or a CPU mapping; a hostile tier-2 display build that writes every address register and SMU address message directly is refused and logged on every attempt; the tier-2 display part made to panic while a Vulkan app renders comes back, and the app keeps running with no device-lost error; 144 Hz frame time meets its target on the reference discrete GPU; a hung engine is reset within 2 seconds without losing the session, and a full adapter reset is measured and published separately; 5 benchmark games run within 15% of Linux (average and 1% low frame rate, worse end of the Holm-corrected 95% confidence interval over at least 20 boots per kernel, against both matched LTS and matched stable); the Phase 5 panic-lock test reruns with a GPU userptr canary, gone from the dump; and the Phase 8 optional-feature test in [design/features.md](design/features.md) passes (the overlay costs at most 0.5% CPU and adds no input-to-display or frame-time latency at 144 Hz on direct scanout). Proof gates: target 4 extended at P/T to GPU buffers; target 13 at B/T. Attack rows: none.

### Phase 10: Performance and lean push
- Profile everything. Tune the scheduler, memory management and I/O paths until the desktop benchmark set beats Linux by the rule in [design/benchmarks.md](design/benchmarks.md) (on server-style throughput, the worse end of each corrected interval within 5% of matched Linux).
- Power management: CPU sleep states, frequency scaling, Thread Director and preferred-core hints, the X3D policy, the deadline scheduling class, and suspend/resume for laptops (microcode reapplied on resume). At suspend the kernel draws a random 256-bit R and seals only R into the resume object (sealed object 5: `TPM2_PolicyCounterTimer` requiring resetCount to equal its value at suspend, PCR 4 and 7, this boot's capped PCR 8 and 9 including the boot nonce, and `TPM2_PolicyAuthValue`; DA-protected); the system volume key, S, the held PIN half, the home and swap keys (in stage 2 also the class A keys and the class B per-file keys) are wrapped into the resume object, encrypted under HKDF(R ‖ second half of the stretched PIN) and kept in RAM only, with the blob, and the plaintext keys and R are wiped; the agents' secret memory is AEAD-wrapped under HKDF(R ‖ PIN half 2), and frozen apps' memory is a named residual of promise 4, defeated only by SME or TME; stage 2's class B and C keys are wiped, because suspend locks first; from Phase 12 open vaults are closed and unsealed travel folders resealed first ([design/storage.md](design/storage.md) "Key inventory"). Resume reads the PIN only through the in-kernel input paths and only from keyboards connected before suspend (a keyboard counts as present if its port path, vendor and product IDs, serial and descriptor hash match after re-enumeration), stretches it in memory reserved before suspending (or freed by dropping clean page cache); a TPM reset during suspend leads to recovery. The S3 waking vector clears Bus Master Enable on every bridge and root port and re-arms the IOMMU before any device or interrupt is re-enabled; where the firmware kept no DMA protection on its S3 path, the boot log, Settings and the scorecard name an "S3 resume DMA window". Hibernation: class-C keys are evicted before the image is written; at hibernate the kernel draws an image key and a random R, seals R (sealed object 4) with the full pre-cap policy (signed PCR 4, 8 and 9, PCR 7, the rollback floor and the PIN), and writes the blob and the image key encrypted under HKDF(R ‖ PIN half 2) into the header block, never into a persistent TPM object, all before S, the volume key and the PIN half are wiped; the image key and the PIN half sit in a reserved page excluded from the image and wiped after the write. The image goes into a dedicated hibernation extent (40% of RAM rounded up to 1 GiB), encrypted under the image key, and records the release and the commit generation (stage 1: the ext4 mount count and journal sequence, with no replay value; stage 2: the commit generation and the replay value, which must equal the current one, since a hibernation resume bumps nothing); after the snapshot only the fixed header area is written. Resume is a boot of the same release (the loader keeps the image's slot) that unseals R before capping and hands the volume key and S to the restored kernel in a reserved page the restored kernel wipes, together with 256 bits for the random generator; the resumed file system draws a new nonce prefix, a hibernation resume bumps nothing, and any normal mount first erases the image blob ([design/storage.md](design/storage.md)).

- Optional features ([design/features.md](design/features.md)): focus boost and background freezing with exemptions (F9, both off by default; an identity with a live direct channel from an unfrozen identity, child identities included, is exempt, and a message queued to a frozen peer thaws it); the per-app power meter from RAPL and GPU energy counters (on) with per-app power caps (off) (F10); and the panic lock's hibernate mode (F4, offered only while exactly one session is logged in, otherwise the panic powers off; the image key is wrapped under the panic key before that key is wiped, the panic key stays wrapped under that user's stretched login passphrase in header-block slot 15, and resume asks for the passphrase on the trusted path and needs no PIN).

**Minimum product.** The kernel through Phase 7 with every security gate
passing (signed updates included), the bootloader, and borrowed userland is a complete, usable,
secure OS. Everything after that improves it. If time runs short, the order
of priority is: kernel phases and their security gates, then the bootloader
and filesystem tracks, then GPU and games, then the other tracks.

**Defer rules.** Every track reports one progress metric (for the browser
engine, its WPT pass rate; for the compositor, its latency against the best
borrowed one). A track whose metric hasn't moved in 12 months is paused and
its borrowed replacement stays, until there's a plan to unblock it. No track
is ever shipped before it meets its done-when, whatever that costs in time.

Honest notes:
- **Bootloader** and **everyday apps** are the most achievable.
- **Filesystem** is very hard to get right, because a bug loses people's files. It gets the heaviest testing of anything here.
- **Web browser engine** is the biggest single project on this list, bigger than the kernel. HTML, CSS and JavaScript each take years. It is a long-running track, and a borrowed browser ships until ours passes its tests.

  - reference machines with AMD SME and Intel TME by Phase 11.
- **Services:** a public transparency log and at least 4 independent witnesses (threshold 2), run by parties other than the release signers, before Phase 4b starts (a 4b entry condition).
- **Signing keys:** hardware tokens for the offline root key (2 of 3) before the first public release, and for the config-signing key (2 of 3) by Phase 4b.
- **Outside audits** at the end of Phases 1, 3, 4a and 4b and before 1.0 (volunteers or funding).
- **Accounts:** shim review submission and Microsoft signing (Phase 4b tests path 1 with a test CA enrolled in db, so it never waits for them), and repository settings.

Until a dependency arrives, the work that needs it is reported as "not yet
measured" or "not yet done", never claimed.

## What we deliberately don't build
- A compiler (Rust/LLVM), and for now the GPU graphics stack (Mesa) and Windows compatibility (Wine/Proton). Those run through the Linux interface and can become "built by us" tracks later.
