# Optimal OS roadmap

Goal: build the best desktop OS there is, starting with our own kernel written
from scratch: fast, lean, safe, and able to run the software people already use.
The kernel comes first (Phases 0 to 11); the full OS is built on top of it (Phase 12).

This is a serious engineering project, not a toy. That means every phase ends
with a test that proves it is done, every performance claim comes from a
benchmark, and nothing merges unless CI builds it, boots it and passes the tests.

This file is the plan. The detailed design, which every phase below must
meet, is in [design/](design/README.md).

## Pillars, in priority order
1. **Performance.** The main focus. Measured against Linux on the same machine, never guessed ([design/benchmarks.md](design/benchmarks.md)).
2. **Security.** An absolute focus. Nobody can read a user's data remotely, and a compromised app can't reach anything it wasn't given. Exactly what that means, against whom, and how each promise is tested is in [design/threat-model.md](design/threat-model.md).
3. **Lean.** Nothing runs unless something needs it. Small memory footprint, fast boot.
4. **Runs on almost anything.** Any 64-bit x86 PC first, ARM64 later. On hardware that lacks a security feature (no TPM, no IOMMU, BIOS only), Optimal still runs and says plainly which protections that machine can't have.
5. **Compatibility.** Runs existing Linux programs unchanged, 64-bit and 32-bit, which is the road to Windows games through Wine/Proton.
6. **User respect.** The kernel does what the user says. No hidden telemetry, ever.
7. **Polish.** Clear error messages, clean crash reports, good docs.
8. **Customisation.** The smallest pillar: boot options, schedulers and modules the user can choose.

**When pillars conflict.** Security features are on by default. The only
reason to make one optional is a measured cost of more than 2% on the
geometric mean of the desktop benchmark set, or more than 5% on any single
desktop metric, recorded on the scorecard with the owner's sign-off.
Mitigations that stop data leaking between processes, or from the kernel to a
process, are never off by default whatever they cost.

## Core architecture decisions

These are decided now because they are expensive to change later.

- **Language: Rust.** Memory-safety bugs cause most serious kernel security holes. Rust removes most of them at compile time with no speed cost.
- **Shape: a "framekernel".** A small core is allowed `unsafe` code: boot, paging, interrupts, context switching and the raw hardware access. Everything else (scheduler policy, filesystems, network stack, drivers) is written in safe Rust on top of that core. This is a memory-safe in-kernel component architecture: it keeps monolithic-kernel speed (no message passing between processes for every operation) and removes most memory-corruption bugs. It is not a hardware isolation boundary the way a microkernel's separate address spaces are: a safe-Rust component still runs with kernel privilege and can still exhaust resources, deadlock, get logic wrong or misprogram a device, and safe Rust is no defence against a hostile author. So in-kernel code is ours or fully audited, third-party drivers run in their own processes, and isolation comes from the driver trust tiers, resource budgets and per-device IOMMU domains in [design/drivers.md](design/drivers.md). The boundary between the core and the rest is enforced by tools, not convention ([design/core.md](design/core.md)).
- **Compatibility through the Linux system-call interface.** Instead of inventing a new interface and waiting for apps to be written for it, Optimal speaks the same system calls as Linux, 64-bit and 32-bit. Linux programs, Mesa, Wayland and eventually Wine/Proton can then run unchanged. This is our own clean implementation of a public interface, so it involves no Linux code. How Linux semantics sit on top of capabilities is in [design/capabilities.md](design/capabilities.md), and the ABI plan in [design/compat.md](design/compat.md).
- **Boot: our own bootloader, "Optimal Boot"**, a UEFI loader in Rust that speaks the Limine boot protocol, checks a signed config and measures everything into the TPM ([design/boot.md](design/boot.md), `bootloader/DESIGN.md`). Until it ships, Limine (BSD-2-Clause) is used, with every file hash-pinned and its config enrolled, in the shipped image as well as the tests (Phase 1 work, not done yet: the current ISO ships stock, unsigned Limine and enrols nothing).
- **First target: x86_64.** ARM64 comes once the core is stable. Code that depends on the architecture lives in its own module from day one.
- **Licence: our own code only, never GPL.**
  - Kernel, bootloader and every component we write: clean-room code from specs (Intel/AMD manuals, ACPI, PCI, NVMe, xHCI and USB specs, the Linux man pages and uAPI docs for the syscall interface). We never copy, translate or read for reference the code of Linux, BSD or other kernels. Dependencies must be MIT, Apache-2.0, BSD, Zlib or similar, checked by `cargo-deny` in CI.
  - Borrowed programs shipped in the OS until ours replace them: permissive licences preferred; weak copyleft (LGPL, MPL) allowed as separate, unmodified programs (Wine, a browser); GPL programs are not shipped, with one exception: shared libraries under the GCC Runtime Library Exception (glibc is LGPL; libstdc++ and libgcc_s are GPL with that exception), which every Linux program links against ([design/compat.md](design/compat.md)). The base system uses dash as `/bin/sh` and uutils for coreutils; bash and other GPL programs are third-party apps the user can install from the store, never part of the image.
  - Firmware: redistributable vendor binaries (CPU microcode, GPU and Wi-Fi firmware) are allowed as data, each listed with its licence and hash ([design/drivers.md](design/drivers.md)).
  - Test tools: GPL test suites and checkers (LTP, xfstests, kselftest, `e2fsck`) may be run as external test oracles, never linked, vendored or shipped.
  - The repo has no licence file yet, which means all rights are reserved until the owner picks one.

## Security model

Security is built in from Phase 1, not bolted on at the end. The threat model,
the trusted computing base, the hardware security tiers and a table of every
attack path with its defence and its test are in
[design/threat-model.md](design/threat-model.md). In short:

- **Memory safety:** Rust everywhere, with `unsafe` kept to a small, size-capped, inventoried core ([design/core.md](design/core.md)). Memory safety is the floor, not the whole answer: logic bugs, races, hardware misuse and DMA mistakes are handled by the measures below.
- **Driver trust tiers:** core, trusted drivers, restricted drivers (all ours, in the kernel), and user-space drivers (anything third party, and anything parsing untrusted input by default), each with its own IOMMU domain and resource budgets, with defined fault containment and restart ([design/drivers.md](design/drivers.md)).
- **Formal verification of the security-critical core:** proofs and bounded checks at stated levels (Kani, Verus, loom) for page tables, the frame allocator, the soundness of the core's safe APIs, process memory isolation, capability derivation and revocation, user-memory copies, resource accounting, the scheduler, the driver boundary, the IOMMU, storage invariants, network packet parsers and the anti-rollback floor state machine, with the kernel's cryptography tested against published vectors. The `unsafe` hardware shims are a separate, tested-only target with a size cap. Each target states its assurance level (proved, bounded, model-checked or tested only) and its assumptions, and the level reported is the weakest of its own and every target its assumptions rest on ([design/verification.md](design/verification.md)).
- **Hardware protections:** no-execute pages, write-xor-execute for all kernel memory, SMEP/SMAP, UMIP, guard pages around every stack, KASLR with a position-independent kernel randomised over at least 2^16 slots and measured entropy, page-table isolation where the CPU needs it, page tables in a separate physical zone with guard rows against Rowhammer, and the IOMMU from Phase 1. Control-flow protection: user-space CET shadow stacks from Phase 5; kernel shadow stacks and indirect-branch tracking as soon as the stable Rust toolchain can build for them, in Phase 11 at the latest (tracked on the scorecard until then). Memory encryption (AMD SME, Intel TME) where the CPU has it, from Phase 11 at the latest, with the scorecard showing whether it is on.
- **Least privilege through capabilities:** a process can only touch objects it holds a handle to; Linux file descriptors are capabilities, with a derivation tree and revocation ([design/capabilities.md](design/capabilities.md)).
- **Every app sandboxed by default:** its own view of the filesystem, no access to other apps' data, and access to the camera, microphone, screen, location and user files only through portals whose prompts are drawn by the system (on a dedicated prompt VT reached by Ctrl+Alt+Delete from Phase 5, by the compositor from Phase 7). Apps start with no file, device or network grants: an identity's first non-loopback `connect` or `send` returns `ENETUNREACH` at once and queues one network request, and no syscall waits on a human. Each request is decided by the user's prompt level, "Always ask", "Only when suspicious" (the default) or "Almost never": it prompts, or is granted silently, logged and revocable in Settings, and the answer is remembered. A closed, tested list says what is suspicious, and a floor always prompts at every level: inbound access, remote control and screen sharing, a new keyboard-like (HID) device, and files plus network for one identity or component (the remote-read promise). Network access is a per-identity egress filter that reaches live sockets: a network grant is outbound only, a wildcard socket receives only loopback traffic unless the app holds an inbound grant for that port, and apps whose component holds file grants get no network access unless the user approves that combination. Files from removable media and downloads carry provenance "removable" or "downloaded", and running one starts a new identity with no grants and no network until the user approves it.
- **IOMMU on by default from Phase 1:** devices can only reach memory handed to them, interrupt remapping on. From Phase 6 every new USB, Thunderbolt and Bluetooth device is held until approved, per USB interface, and while the screen is locked all USB and Thunderbolt ports refuse new devices. Machines without an IOMMU are told so; there, device-read descriptors hold only typed addresses of granted buffers and DMA-address registers are written only by the core, so driver bugs can't aim DMA at kernel data, but a malicious device or radio firmware can, and radios stay off until the user accepts that named exposure.
- **Encryption by default:** Phase 4a encrypts the disk (AES-XTS, confidentiality only); the own filesystem then adds authenticated, per-user encryption with keys evicted on lock ([design/storage.md](design/storage.md)). Keys are sealed to measured boot with a signed TPM policy plus a PIN where there's a TPM, a passphrase where there isn't, and a recovery key is always created. Every sealed TPM object seals only a random value R, and the key material it guards is encrypted under HKDF(R ‖ half of the stretched PIN), so someone who extracts the TPM's secrets still faces a PIN search. Every PIN and passphrase is stretched with Argon2id under one rule (memory min(1 GiB, RAM/4) but at least 64 MiB, at least 4 passes), so an encrypted install needs at least 256 MiB of RAM.
- **Verified and measured boot:** firmware checks the bootloader, the bootloader checks a signed config that pins the kernel and the system image's hash tree root, and every step is measured into the TPM. Anti-rollback, A/B slots, boot counting and a recovery image are in [design/boot.md](design/boot.md).
- **Nothing listening by default:** no remote-access services, a default-deny inbound firewall.
- **Lockdown:** no interface lets anyone, root included, load unsigned ring-0 code or read kernel memory ([design/threat-model.md](design/threat-model.md)).
- **Signed updates only,** with a TUF-style key hierarchy, an offline root, a transparency log whose checkpoints at least 2 independent witnesses cosign, reproducible builds and anti-rollback; the update client ships in Phase 7, so the minimum product can be patched.
- **CPU side-channel mitigations** chosen per CPU model after microcode is loaded, including Spectre v1 index masking in safe Rust parsers; GDS is mitigated by microcode or by turning AVX off through XCR0; SMT is off by default on CPUs affected by MDS, L1TF, TAA or RFDS, and core scheduling is an opt-in for app-to-app isolation only (on by default only where siblings can't leak kernel data); costs benchmarked and published.
- **Testing security like everything else:** every attack path in the threat model has a test that becomes a gate in the phase it lands; continuous syscall, network, device-side and filesystem fuzzing; outside audits of the core at the end of Phases 1, 3, 4a and 4b and before 1.0.

## How we know it is good

- **CI on every change:** build, `rustfmt`, `clippy` with warnings as errors, the in-kernel tests and a boot matrix in QEMU: 64 virtual PCs (BIOS and UEFI, old and new chipsets, 128 MiB to 8 GiB of RAM, 1 to 16 cores), each booted 3 times. Lands in Phase 1: Limine and every other download pinned by SHA-256 and GitHub Actions by commit hash, the core's lint rules, the unsafe inventory and core size check, `cargo-deny` and `cargo-vet`, and the gate-table check below. Lands in Phase 1a: the exact Rust toolchain pin (a version, not a channel name) in `kernel/rust-toolchain.toml` and `bootloader/rust-toolchain.toml`, with a CI check that rejects a channel name in any `rust-toolchain.toml`, and the proofs job, with Miri on the host tests of every pure tier-0 crate. loom lands in Phase 1c (single-CPU interrupt re-entry and the page-table walker thread) and shuttle in Phase 2.
- **Gate tables match the plan** (lands in Phase 1): a CI script checks that every proof target and level change in [design/verification.md](design/verification.md), every attack row in [design/threat-model.md](design/threat-model.md) and every compatibility milestone's suite and target in [design/compat.md](design/compat.md) is named in the done-when of the phase its table gives, that no done-when below names a gate those tables put in another phase, and that every proof level is written own/effective.
- **No silent skips.** A test that can't run (missing firmware, missing tool) fails CI unless it is on a checked-in allowlist with a reason. A green run means everything listed actually ran. Compatibility pass rates use one skip rule, the same as [design/compat.md](design/compat.md): every skipped test counts as a failure, and a test on the phase's excused list is shown separately and still counts against the rate.
- **Nightly soak:** the same matrix booted 40 times per configuration (over 2,500 boots) to catch rare, timing-dependent bugs. Soak tests grow with every phase: hour-long scheduler stress, file system crash-state runs, driver kill-and-restart loops, continuous fuzzing.
- **In-kernel test suite** (from Phase 1): unit tests that run inside the kernel under QEMU, so allocators, page tables and the scheduler are tested in the real environment.
- **Tough but realistic conditions** (from Phase 1): every change also boots on deliberately awkward machines: CPUs from Core 2 to current Xeon/EPYC with security features missing, 5-level paging, odd core topologies, NUMA (including a node with no memory), odd and split memory, no HPET, no ACPI, old and new OVMF builds, a host fighting for CPU, and Secure Boot attacks (unsigned bootloader, wrong key, tampered kernel, tampered config, old signed image), which must be refused. Fault injection joins as each piece lands: failed allocations, quirky ACPI tables, timer jitter, spurious interrupts, hostile DMA devices, then disk power cuts and I/O errors.
- **Public scorecard from the first bootable build:** performance against a pinned, matched Linux baseline (booted with the same SMT setting, `nosmt` on affected CPUs), measured on dedicated bare-metal machines driven by a separate controller host (shared CI VMs are too noisy and are used for functional tests only), with the latency tracer off in every benchmark boot and its enforcing stress boots in their own slot (1 hour a day on the gate machine). Non-tail metrics get at least 3 runs in each of at least 20 boots per build. Tail metrics (P99 and above, variances) pool their events per boot, treat the boot as the cluster and need at least 20 boots per kernel, gathered in rolling windows (the nightly block judges the last 5 nights, the extended microbenchmark block the last 4). Every machine is scheduled under 168 hours a week, and a scorecard release comes at most once per 4-week release cycle. The release rule compares each release with the last one: the one-sided 95% upper bound of the difference is at most 3% worse for every non-tail metric, at most max(3%, 3.29 × its SE) worse for every tail metric, and at most 0.5% worse for the geometric mean of the desktop set's non-tail metrics (SE of the geometric mean at most 0.15%). Every phase gate uses one decision rule: an absolute target is met when the one-sided 95% bound on the worse side meets it; a comparative gate (against Linux, the last release or another Optimal path) is met when the worse end of the Holm-corrected two-sided 95% confidence interval meets it, over at least 20 boots per kernel, against both matched LTS and matched stable Linux; and "no worse than matched Linux" means the one-sided bound of Optimal/Linux is at most 1 + max(2%, 3.29 × SE). Committed provisional targets can only tighten, and a security scorecard per hardware tier counts only what is on in the shipped image. See [design/benchmarks.md](design/benchmarks.md).
- **Formal verification in CI:** every proof target runs on every change, with up to 20% of each target's harnesses run nightly instead, with time budgets and tracked bounds ([design/verification.md](design/verification.md)).
- **Fuzzing:** syscalls from Phase 3, the driver boundary, device-side driver fuzzing, the boot keyboard readers and filesystems from Phase 4a, the pre-cap Optimal header block parser from Phase 4b, each user-space trusted service's protocol (10^8 executions) from the phase it lands in (5 to 7), the network stack, Wi-Fi, Bluetooth, USB descriptors and the udev-compatible daemon from Phase 6.
- **What runs today and what lands later.** Each item above is marked on the scorecard as running now or "lands in Phase N"; nothing is described as running before its job exists.
- **Real hardware:** from Phase 1, each milestone is also checked on at least one real PC booted from USB.

## Phases

Each phase ends with a "done when" test, and every item listed in a phase is
part of that test: if a phase builds something, its done-when checks it. Work
that depends on a phase doesn't ship until that phase's done-when passes.
Work that doesn't depend on it (the built-by-us tracks, proofs, fuzzing,
security items) runs in parallel and is never held back by a later, unrelated
phase. In particular, no security item waits for GPUs or games.
Phase 1 has lettered parts (1a to 1d). Storage and the trusted boot chain
are two lettered phases, 4a (storage) and 4b (trusted boot chain), and
every item of that work names its phase, never both at once.
The file system track starts after 4a.
Each done-when ends by naming the proof targets and their levels, always
written own/effective (for example "P/T" or "T/T")
([design/verification.md](design/verification.md)) and the attack rows
([design/threat-model.md](design/threat-model.md)) that gate in that phase.

### Phase 0: It boots (done in CI)
- Rust kernel loaded by Limine, writes to the serial port, paints the screen and reports usable memory.
- CI builds the kernel, makes a bootable ISO, boots it in QEMU on BIOS and UEFI, and uploads the ISO.
- Done when: CI is green and the ISO boots on a real PC from a USB stick, showing the blue screen band.

### Phase 1: The core
- **1a, CPU setup:** GDT, TSS, IDT, and handlers for every CPU exception with a clear crash report (registers and a stack trace); a double-fault handler on its own IST stack so stack overflows are reported; the proofs CI job and Miri land; the exact toolchain pin in `kernel/` and `bootloader/`; the bootloader workspace falls under the core's rules from here (its tier-0 crates capped at 3,000 lines, of which shim code is at most 1,500, [design/core.md](design/core.md)).
- **1b, memory:** physical frame allocator (NUMA-aware), our own page tables for the kernel, a fallible kernel heap, guard pages; the memory-access backend (phys-to-virt and entry accessors behind a trait the pure crates are generic over, about 150 lines in `core-mm`, with its shim contract and CI check); the kernel built position-independent, picking its own virtual base over at least 2^16 slots at 2 MiB granularity, and its direct-map base, when it builds its own page tables (KASLR, the same under Limine and Optimal Boot); its physical load address is chosen by the loader, and under Limine the scorecard reports physical KASLR as "not done until Optimal Boot"; the first proofs of memory targets.
- **1c, ACPI, interrupts, IOMMU and time:** ACPI tables, AML hosting staged as in [design/drivers.md](design/drivers.md) (safe Rust, fuzzed, confined; a SystemMemory access that overlaps any ECAM range goes through the same PCI config filter as a PCI_Config access, which refuses writes to BARs, the command register, MSI and MSI-X, ACS and Device Control 2 of every function, assigned or not), minimal PCI enumeration (enough to find and program the IOMMU), local APIC and I/O APIC, the IOMMU in deny-all mode (every unused Intel context entry and all 65,536 AMD-Vi device table entries per segment blocking DMA and interrupts; Intel in scalable mode when ECAP.SMTS is set and translation is off at hand-off, else the inherited or legacy mode; AMD rewriting inherited device-table entries in place) with interrupt remapping (every IRTE with SVT=01 and the exact requester ID), requester-ID aliases (bridges, DMAR and IVRS aliases, phantom functions, the quirk table) sharing the device's domain and group, the viable-group rule (a domain never mixes a tier-3 device with a tier-1 or tier-2 device), and bus mastering cleared on every bridge and root port and then every function in the defined order ([design/drivers.md](design/drivers.md)), kept off until assigned. DMA is stopped by the bridge or root-port Bus Master Enable plus the IOMMU, never by a device's own BME. Exempt: the IOMMU's own function, the firmware display and the bridges on its path, and USB host controllers still owned by the firmware and the bridges on their paths, which stay with the firmware (BME on, in a domain holding only their RMRRs) until the Optimal driver that runs them starts. On D2 machines only, BME stays clear on every external port (one with the ACPI `ExternalFacingPort` property, in a Thunderbolt or USB4 topology, or named by a DMAR SATC entry, never a port with only the Hot-Plug Capable bit); below a hotplug-capable port that isn't external, devices present at boot may master and devices added after boot are refused. Boot-services and bootloader-reclaimable memory is not reused until bus mastering is cleared and the IOMMU is live. A machine with no firmware pre-boot DMA protection shows the named "boot DMA window" exposure. Time: a TSC invariance check, calibration from CPUID leaves 15h/16h, else HPET or the ACPI PM timer, else the PIT, and a clocksource watchdog; timer events from the LAPIC TSC-deadline mode, falling back to LAPIC one-shot, HPET, then PIT; the clock-drift exchange on the 16550 UART. Microcode loaded on the boot CPU before mitigations are chosen. loom starts with the single-CPU interrupt re-entry models and the page-table walker thread.
- **1d, console:** a framebuffer text console so the kernel can talk without serial (with a font we make or that is permissively licensed).
- The kernel becomes a workspace with tier-0 crates and enforced lint rules, the unsafe inventory and the core size cap ([design/core.md](design/core.md)).
- Security baseline: no-execute, write-xor-execute kernel mappings, SMEP, SMAP, UMIP, guard pages, KASLR. The shipped image moves to the hash-pinned, enrolled Limine chain (not done yet: the current ISO ships stock, unsigned Limine and enrols nothing), keeping the BIOS image for B4, with a CI check that fails the release build unless the ISO's `limine.conf` hash is enrolled in its Limine binary. Supply chain: the exact toolchain version, Limine's SHA-256 and every other build input pinned.
- In-kernel test runner in CI, plus the tough-conditions run and Secure Boot attack tests. The "old signed image refused" test puts the old image's hash in dbx in the test OVMF variable store, because Limine has no security version number.
- The hostile-device emulator: our own vfio-user device server (permissively licensed, built on libvfio-user), attached to an unmodified QEMU at a pinned version used as an external test tool.
- First scorecard entries: boot time, timer accuracy, kernel memory, and the security table.
- Where it runs today: CI covers QEMU boots, the in-kernel tests and proofs as each lands; real-hardware and bare-metal items are reported "not yet measured" until the owner's machines are online.
- Done when: every exception type is triggered on purpose in tests and reported correctly; the allocator and page tables pass their tests; every tough-conditions scenario passes; the KASLR tests in [design/boot.md](design/boot.md) pass (an SP 800-90B estimate of at least 9 bits for the picker's output over 10^6 host draws, a 90B estimate for each raw source: EFI_RNG, RDRAND/RDSEED and the TSC fallback; and at least 95 distinct bases in 100 QEMU boots); boot time from firmware handoff to kernel ready is under 300 ms on the reference desktop (mean over 20 boots, one-sided 95% bound); the timer drifts under 1 part per million over a 10-minute run on the dedicated KVM host, with QEMU's CPUID level at least 0x15 and an explicit `tsc-frequency` read by the guest from CPUID 15h, measured as the least-squares slope of the kernel's once-a-second clock lines on the 16550 UART (polled, no DMA) against their arrival times taken on the host with `CLOCK_MONOTONIC_RAW` (never against the calibration source, and never on hosted runners, whose clock is itself a guest clock; the bare-metal drift test is in Phase 2); the Secure Boot attack tests refuse an unsigned bootloader, a wrong key, a tampered kernel, a tampered config and an old signed image (through its dbx hash entry); the release build's enrolment check runs; QEMU `usb-ehci` and `piix-uhci` controllers, and a `qemu-xhci` behind a `pcie-root-port`, stay with the firmware, BME on along their path, in a domain holding only their RMRRs; the IOMMU tests run on QEMU's Intel IOMMU once in legacy mode and once with `x-scalable-mode=on`, and on its AMD IOMMU; devices behind a `pcie-pci-bridge` do DMA and MSIs that work, and a sibling behind the same bridge is in the same group; behind a port without ACS, a device with a tier-3 driver next to one with a tier-1 driver is refused, and is given the whole group when it is the only driver; a hostile DSDT that writes ECAM through a SystemMemory region and sets BME on a hotplug-capable port and on an unassigned bridge is refused and logged on every attempt; a QEMU machine with no IOMMU boots from an NVMe device behind a hotplug-capable `pcie-root-port` and does I/O through it, while an NVMe device added with `device_add` under a second such port gets no BME and no driver; the boot DMA window is reported on OVMF without pre-boot protection; the gate-table check runs; and the outside audit of the Phase 1 core is done with its findings fixed. Proof gates at 1a: target 3a at B/T per tier-0 API for panics, bounds and functional behaviour; target 3a at T/T for aliasing (Miri); target 3b at T/T for each shim; target 3c at T/T (`with_irqs_disabled`, IRQ and preemption tokens). At 1b: target 1 at B/T; target 2 at B/T (owners: allocator and page tables); target 3b extended at T/T (memory-access backend). At 1c: target 1's A/D-bit and walker clause at B+M/T (loom walker thread); target 3a's interrupt re-entry at M/T (single CPU); target 3b extended at T/T (IOMMU register and queue programming, PCI config, MSI-X); target 3c extended at T/T (MMIO, port I/O, IRQ and DMA handles); target 10 at B/T. Attack rows: A4 → poisoned dependency; A5 → DMA attack (1c: the vfio-user hostile device server on QEMU `intel-iommu` and `amd-iommu`, on the root bus and behind a root port, sending DMA and MSI writes outside its domain and from an unassigned requester ID, compatibility-format MSIs, a fault storm and DMA across the firmware hand-off).

### Phase 2: Many cores and a scheduler
- Start every CPU core (SMP), with per-core data, microcode on every core, and the typed locking and per-CPU rules in [design/core.md](design/core.md), checked by a lock-order checker.
- The scheduler in [design/scheduler.md](design/scheduler.md): fully preemptible kernel, real-time, fair (EEVDF) and idle classes, threaded interrupt handlers, priority inheritance for kernel locks, topology and capacity-aware placement for hybrid CPUs, high-resolution timers, a tickless idle and the single-thread tick stop (a CPU running one thread stops its tick).
- Frequency control with hardware P-states (Intel HWP, AMD CPPC). From here it is a precondition of every comparison with Linux, the Phase 4a storage set included. Microbenchmarks run with turbo off and HWP or CPPC minimum = maximum = 80% of guaranteed performance on both kernels; desktop, real-time-latency and throughput metrics run at shipped defaults with the same energy-performance preference on both.
- Kernel threads, sleeping, wake-ups and timers.
- The latency tracer, whose trace points switch between their two precompiled states through the core's text-poke path (a temporary private writable mapping, the `int3` and IPI cross-modifying-code protocol, direct-map aliases of kernel text read-only). It reports only in VMs, is enforced in dedicated bare-metal stress boots (1 hour a day on the gate machine) and is off in every benchmark boot. shuttle starts with the multi-CPU models.
- The benchmark harness lands here, with Optimal compared against **itself** only (there is no user space yet to compare with Linux fairly), plus the first dedicated bare-metal runner and its rig ([design/benchmarks.md](design/benchmarks.md)): a controller host, not the machine under test, boots the runner over UEFI HTTP or PXE, power-cycles it through a relay and on a watchdog, and captures checksummed results over serial; it carries a GPS receiver whose PPS pulse drives each runner's UART DCD pin; only maintainer-approved commits run, on an isolated network with no secrets. `isolcpus` is used only for the per-change microbenchmark tier; every desktop, real-time-latency and throughput metric runs on the default boot with no isolated CPUs. Microbenchmark runs during which an SMI arrived are discarded and rerun; tail-latency runs keep every sample and publish the SMI count.

### Phase 4b: The trusted boot chain
- Entry conditions: Optimal Boot's measured boot and boot counting have landed (bootloader track), with the loader's `ed25519-dalek` and `sha2` replaced by `core-crypto`; Secure Boot path 2 works on the reference laptop; and the owner-provided transparency log and at least 2 independent witnesses are running.
- The TPM 2.0 driver: MMIO and the TPM service in tier 0, the protocol in a safe tier-1 crate. The TPM service lives in the kernel and alone holds raw TPM access; user space reaches the TPM only through the TPM broker API, whose only operation is to unwrap a user key (no hibernation-key sealing, replay-counter bump or lockout reset). The signed TPM policy over PCR 4 (path 1 and path 2 variants), 7, 8 and 9, PIN and recovery, TPM ownership, with parameter encryption ([design/boot.md](design/boot.md)). Objects that bind PCR 4 per machine use a separate policy reference, `optimal-disk-v1-pm/f`, the only one PCR 8/9-only digests are signed under, and the counter's policy branches bind the same way. Optimal Boot measures its own security version number, then the config-signing key ID, into PCR 8. The PIN is stretched under the KDF rule of Phase 4a and mixed into the key; on firmware-TPM machines a passphrase of at least 60 estimated bits is required instead. Optimal Boot reads the PIN through UEFI `ConIn` before `ExitBootServices`, above an anti-phishing TOTP code (RFC 6238) from a sealed HMAC key that the user checks against their phone; the TOTP key is bound to the signed PCR 4, 8 and 9 policy and the floor, never PCR 7, the kernel records the RTC-to-UTC offset at shutdown, and a re-enrolment flow covers a boot that shows no code. The loader warns when the PCR 7 log shows Secure Boot off or PK, KEK or db changed (without a firmware setup password a correct code doesn't prove the firmware unchanged, a residual on the scorecard). Dictionary-attack lockout: 32 tries, recovery time 7,200 s, lockout recovery 86,400 s; `TPM2_Shutdown(CLEAR)` on every reboot, power-off and panic path and `TPM2_Shutdown(STATE)` at suspend; the kernel resets the lockout counter before capping after every good disk-secret unseal, with the lockout secret it holds wrapped under the service-key secret.
- Optimal Boot accepts only configs signed (Ed25519) by the config-signing key: offline, held 2-of-3 on hardware tokens as a delegated TUF role, its public half built into the loader, revoked by a loader with a higher SVN, and rotated in a fixed order (configs dual-signed in the other slot and both recovery copies, then the loader update, then the floor raise). Each config carries a transparency-log inclusion proof and a checkpoint cosigned by the witness set built into the loader (at least 2 witnesses, threshold 2, changed only by a signed loader update). Before `ExitBootServices` the loader does all of its firmware I/O, then sets up a deny-all IOMMU, then calls `ExitBootServices`, then re-checks the IOMMU and re-arms it if a firmware handler turned it off, before handing over; it builds its tables in the kernel's translation mode, the deny-all exceptions are the RMRRs and the firmware framebuffer (read-only), and where it can't program translation it uses PMRs, which count only if they cover every page the kernel and loader occupy. It disables the platform hierarchy if the firmware left it open.
- Sealing happens at the first boot from disk, never in the installer: the installer sets the TPM's owner and lockout authorisation, creates the SRK, and writes the Optimal header block with the volume key wrapped under the recovery key and the volume tag. The first boot unwraps the volume key from the header block with the recovery key (no boot path reads a LUKS2 key slot), checks the volume tag and caps; after capping it replays its own PCR 4 and PCR 7 log, picks the PCR 4 variant, creates the service key, the mark key and sealed objects 1 to 3, and defines the anti-rollback counter, its base and the TOTP time index with the owner secret the recovery key unwraps. Each new object is checked by comparing a trial-session policy digest with its authPolicy, because a real test-unseal can't run after capping; the second boot unseals with the PIN alone before capping, which is the real test.
- The Optimal header block is the only part of the data volume read before capping: the last 16 KiB before the LUKS2 data offset, which is fixed at 16 MiB, in two 8 KiB copies, each starting with a magic that names the stage, then a version and a CRC-32C, holding the KDF parameters, the SRK and base-index names, the volume tag and up to 14 fixed 512-byte slots (the sealed blobs, the volume key wrapped for each way Optimal opens it, the encrypted S, the owner and lockout secrets). The volume tag is HMAC-SHA-256 keyed from the volume key over both LUKS2 header copies (binary headers and JSON areas) and the header block's fields other than the tag and the slots; it is checked before S is unsealed and before any JSON is parsed, and the kernel uses a LUKS2 header copy only if the tag verifies it, never choosing one by seqid. Its parser is proof target 15's pre-cap part and is fuzzed to the in-kernel thresholds, with both stage magics and unknown ones in the corpus.
- PCRs 8 and 9 are capped unconditionally, whatever the unseal result (passphrase fallback included), before any byte of the data volume beyond the Optimal header block is parsed; the LUKS2 JSON and the volume map are parsed only after capping. Sealed objects 1 to 3 are the list every floor raise and every predicted PCR 7 reseal covers: the disk secret, the service-key secret S and the anti-phishing TOTP key with its mark secret; objects 4 (the hibernation key) and 5 (the resume object) come in Phase 10. Every object with the PIN step seals only a random 256-bit R, and the key material it guards is encrypted (XChaCha20-Poly1305) under HKDF(R ‖ second half of the stretched PIN) and stored in the header block, so the TPM never releases key material. S carries `TPM2_PolicyAuthValue` (the stretched PIN) and is unsealed only after the volume tag matches. The secrets the kernel holds after capping (each R, the TOTP key and mark secret, both stretched-PIN halves) are kept encrypted under HKDF(S, `optimal-held`). Objects used after capping (per-user home keys and the storage replay counter) carry `TPM2_PolicySecret` against the service key, so only a kernel that passed the pre-cap check can use them.
- Anti-rollback: the floor is the NV counter's value minus a base kept in a write-once NV index, both defined at the first boot from disk, and the counter's authPolicy uses `TPM2_PolicyAuthorize`, so the disk policy key can rotate. Raising it takes two boots: after the health check (local checks only), user space writes the other slot and both copies of the recovery image at the new SVN, verifies them, and writes a "commit SVN n" request into loader state; on the next boot the kernel (B1, before capping) or the loader (B2) raises the floor. On B1 the kernel reseals objects 1 to 3 at the new floor, checks each new object's authPolicy against a trial-session policy digest, writes the set into the other header-block copy, and only then increments the counter; the next boot's unseal before capping is the real test, and a boot that resumes from hibernation leaves the request pending. Every predicted PCR 7 reseal (dbx, db, firmware, shim or SbatLevel) reseals objects 1 to 3 the same way. On B2 machines (no TPM) the floor is a boot-services-only UEFI variable; if it is missing or corrupt the floor is max(the minimum config SVN built into the loader, the highest SVN among the configs on the ESP), and the scorecard says B2 anti-rollback holds against OS-level attackers only (against physical ones only with owner keys).
- TPM clear detection: the SRK name and the base-index name are recorded in loader state and the header block; if either changes, the floor is max(the minimum config SVN built into the loader, the highest SVN present), the loader warns and shows no code, and older loaders stay retired through SBAT and dbx, which survive a clear.
- Two loader directories, each with its own `Boot####` entry, plus the `\EFI\BOOT\BOOTX64.EFI` fallback: an update writes the inactive directory, verifies it and trial-boots it with `BootNext` (its own tries counter, at most 3 trials), and `BootOrder` moves to it only after user space marks it good; an SBAT or dbx revocation is applied only after both directories and the fallback carry the new generation. A failed loader-state write boots the current slot, reports, and stages nothing.
- Optional features ([design/features.md](design/features.md)): the tamper alert (F7, on by default): an S-authenticated record of each good boot's event log for PCRs 0 to 5, 7, 8 and 9, compared at the next boot and listed in plain English after unlock, with Optimal's own changes marked expected.

### Phase 8: Real GPU drivers
- The hardest part of any new kernel. Start with one family (AMD or Intel) and work towards accelerated 3D through Mesa, split into a small, size-capped tier-1 GPU core, display and power code in the tier-2 framework, and tier-3 management, under the written clean-room process ([design/drivers.md](design/drivers.md)). The driver targets the reference desktop's discrete GPU, the model fixed before Phase 5. Every GPU page-table entry is built only from a `DmaBuffer`, `Iova` or `VramBuffer` handle (a VRAM range the kernel allocated to that buffer object and cleared), on D1 and D2 machines alike. VRAM and GTT buffer objects are cleared by the GPU's copy or clear engine before their first mapping, with the cost benchmarked and on the scorecard. Display surface, cursor and LUT address registers and the SMU messages that pass a DRAM address are core-only operations. A fault in the tier-2 display part stops only that sub-function (its accessor and core-only operations revoked, display init re-run without FLR), escalating to an adapter reset only if that fails. The GPU's own firmware (GuC, MES, PSP, SMU) is listed in the trusted base and the firmware ledger. Compatibility milestone 11.
- Optional features ([design/features.md](design/features.md)): the game mode overlay (F8, off by default): frame time, P99 and P99.9, estimated input latency and top CPU users, drawn by the compositor on its own hardware plane.
- Done when: Mesa runs hardware-accelerated OpenGL and Vulkan on one GPU family; the milestone 11 suite (Mesa's tests, piglit, the pinned Vulkan Conformance Test Suite subset and the IGT subset) reaches 90% on each, and 100% of its security-class tests; the cross-process GPU buffer isolation test passes; a canary written into VRAM and GTT buffers and freed (including through a context kill and an adapter reset) is never read back by another process through the GPU or a CPU mapping; a hostile tier-2 display build that writes every address register and SMU address message directly is refused and logged on every attempt; the tier-2 display part made to panic while a Vulkan app renders comes back, and the app keeps running with no device-lost error; 144 Hz frame time meets its target on the reference discrete GPU; a hung engine is reset within 2 seconds without losing the session, and a full adapter reset is measured and published separately; 5 benchmark games run within 15% of Linux (average and 1% low frame rate, worse end of the Holm-corrected 95% confidence interval over at least 20 boots per kernel, against both matched LTS and matched stable); and the Phase 8 optional-feature test in [design/features.md](design/features.md) passes (the overlay costs at most 0.5% CPU and adds no input-to-display or frame-time latency at 144 Hz on direct scanout). Proof gates: target 4 extended at P/T to GPU buffers; target 13 at B/T. Attack rows: none.

### Phase 9: Games and Windows apps
- Run Steam, Wine and Proton on the Linux syscall layer (milestone 13), with Steam's manifest-declared shared channels to the games it starts, a virtual-gamepad portal whose `uinput` accepts only gamepad codes, and Steam Input's keyboard and mouse emulation through the compositor's virtual keyboard and pointer behind its grant. Steam ships unpackaged, so the system image carries a signed Steam manifest for the official Steam path and launch closure (and a mapping of Flatpak Steam's metadata onto the same grants), an input to this phase. `modify_ldt` lands with an espfix64-style per-CPU read-only alias stack, so an `IRET` to a 16-bit stack segment leaks no kernel stack bits. Fix what breaks, one game at a time, from a published test list.
- Kernel-level anti-cheat (Valorant, some Call of Duty and EA titles) is a Windows kernel driver and won't run here; the list says so per game. User-mode anti-cheat with Proton support (Easy Anti-Cheat, BattlEye) is a supported target, with named test titles whose anti-cheat probes are run and published.
- Done when: the milestone 13 suite reaches its target (90%, and 100% of its security-class tests), including the shared-channel, virtual-gamepad and virtual keyboard and pointer tests and a Steam update of a game and of Proton after which the game relaunches with no `EACCES` and keeps its grants and home; and a published list of 20 popular games runs, with frame rates compared against Linux and Windows on the same PC. Proof gates: none. Attack rows: A3 → 16-bit stack leak.

### Phase 10: Performance and lean push
- Profile everything. Tune the scheduler, memory management and I/O paths until the desktop benchmark set beats Linux by the rule in [design/benchmarks.md](design/benchmarks.md) (on server-style throughput, the worse end of each corrected interval within 5% of matched Linux).
- Power management: CPU sleep states, frequency scaling, Thread Director and preferred-core hints, the X3D policy, the deadline scheduling class, and suspend/resume for laptops (microcode reapplied on resume). At suspend the kernel draws a random 256-bit R and seals only R into the resume object (sealed object 5: `TPM2_PolicyCounterTimer` requiring resetCount to equal its value at suspend, PCR 4 and 7, this boot's capped PCR 8 and 9, and `TPM2_PolicyAuthValue`); the volume key and S (in stage 2, every per-user, class and per-file key) are encrypted under HKDF(R ‖ second half of the stretched PIN) and kept in RAM only, with the blob, and the plaintext keys, R, the home keys and the held PIN half are wiped. Resume reads the PIN only through the in-kernel input paths and only from keyboards connected before suspend, stretches it in memory reserved before suspending (or freed by dropping clean page cache); a TPM reset during suspend leads to recovery. Hibernation: class-C keys are evicted before the image is written; at hibernate the kernel draws an image key and a random R, seals R (sealed object 4) with the full pre-cap policy (signed PCR 4, 8 and 9, PCR 7, the rollback floor and the PIN), and writes the blob and the image key encrypted under HKDF(R ‖ PIN half 2) into the header block, never into a persistent TPM object. The image goes into a dedicated hibernation extent (40% of RAM rounded up to 1 GiB), encrypted under the image key, and records the release, the commit generation (stage 1: the ext4 mount count and journal sequence) and the replay value; after the snapshot only the fixed header area is written. Resume is a boot of the same release (the loader keeps the image's slot) that unseals R before capping and hands the volume key and S to the restored kernel in a reserved page the restored kernel wipes, together with 256 bits for the random generator; the resumed file system draws a new nonce prefix, a hibernation resume bumps nothing, and any normal mount first erases the image blob ([design/storage.md](design/storage.md)).
- Optional features ([design/features.md](design/features.md)): focus boost and background freezing with exemptions (F9, both off by default); the per-app power meter from RAPL and GPU energy counters (on) with per-app power caps (off) (F10); and the panic lock's hibernate mode (F4).
- Done when: Optimal beats matched Linux on the desktop set on two different real PCs by the rule in [design/benchmarks.md](design/benchmarks.md) (every desktop metric at parity, its Holm-corrected 95% confidence interval within ± its parity margin, against both matched LTS and matched stable: 2% for a non-tail metric, with an SE target of 2% / (c + 1.96), 0.39% for 10 metrics, and max(2%, (c + 1.96) × its SE) for a tail metric, fixed from the previous release's runs, where c is the strictest Holm critical value of the set; and the geometric mean of the desktop set's non-tail metrics better, its corrected interval entirely on the better side); battery life on the three defined workloads is no worse than matched Linux's (one-sided bound of Optimal/Linux within 1 + max(2%, 3.29 × SE), 20 runs per workload); after suspend a stage-1 memory scan finds no volume key, home key or S and no canary from a stage-1 home (stage 1 has its own canary set, with no class C), and the resume PIN is typed on PS/2, USB (with the Phase 6 xHCI driver bound) and serial keyboards, and not accepted from a keyboard attached during suspend; with the TPM's seeds extracted (a swtpm state dump) plus the RAM dump, recovering the keys still needs the Argon2id PIN search, and so does the hibernation blob; resume after a forced TPM reset can't use the resume object and reaches recovery; a reboot that replays the published PCR 8 and 9 events fails to unseal the resume object; a hibernation image holds no class-C key or canary, and resume without the PIN, with tampered PCRs, with an image below the rollback floor, with a different release, or after a normal boot mounted the volume is refused; the keys handed to the restored kernel are gone from the reserved page after resume; the Phase 4b sealed-object suite reruns with a real hibernate and resume; and the Phase 10 optional-feature tests in [design/features.md](design/features.md) pass (freezing exemptions and thaw within 100 ms, focus boost frame time and compile-time bounds, power attribution within 10% and caps within 10%, and a panic-hibernate image holding no key canary). Proof gates: none. Attack rows: A6 → TPM secrets extracted (fTPM break) (the resume and hibernation blobs); A6 → TPM reset or lost state on resume; A6 → locked or suspended laptop (suspend: no volume or home key in memory, the secret asked again on resume); A6 → hibernation image.

### Phase 11: Hardening and release
- Full-time fuzzing in CI, kernel CET shadow stacks and indirect-branch tracking if an earlier phase hasn't landed them (this phase at the latest), memory encryption (AMD SME, Intel TME) where the CPU has it if an earlier phase hasn't turned it on (this phase at the latest), the final outside audit of the core before 1.0.
- ARM64 port.
- Customisation: selectable schedulers and boot options.
- Done when: each item above has passed its own check (audit findings fixed, fuzzing running with no open crash older than 30 days, ARM64 passing the same boot matrix and test suite on QEMU and one real board); a kernel ROP and a forward-edge hijack test both fault; on a reference machine with SME a canary page written through an encrypted mapping reads as ciphertext through a C-bit-clear alias, and on one with TME `IA32_TME_ACTIVATE` reads enabled and locked; and a month of nightly builds on test machines has no crash. Proof gates: none. Attack rows: A3 → kernel (kernel CET; gated in the earlier phase where kernel CET lands, if it does); A6 → DRAM read (cold boot, bus probe).

### Phase 12: The Optimal OS
- Updates driven from the settings app and store, on the Phase 7 update client.
- One settings app, one app store, one app format (with manifests per [design/capabilities.md](design/capabilities.md)), and a GUI for every common task. Flatpak, AppImage and plain tarballs keep working.

Proof gates: none. Attack rows: none.

## Linux compatibility milestones

Linux programs depend on far more than syscall numbers. Compatibility is
split into 13 milestones, from ELF execution to Wine and Proton, each with a
pinned test suite that runs in CI and whose results (by outcome, never one
blended number) go on the scorecard. The full table, the ABI decisions
(32-bit support, kernel identity, `ENOSYS` for anything missing, io_uring and
eBPF) and the measurement rules are in [design/compat.md](design/compat.md).

**Minimum product.** The kernel through Phase 7 with every security gate
passing (signed updates included), the bootloader, and borrowed userland is a complete, usable,
secure OS. Everything after that improves it. If time runs short, the order
of priority is: kernel phases and their security gates, then the bootloader
and filesystem tracks, then GPU and games, then the other tracks.

**Defer rules.** Every track reports one progress metric (for the browser
engine, its WPT pass rate; for the compositor, its latency against the best
borrowed one). A track whose metric hasn't moved in 12 months is paused and
its borrowed replacement stays, until there's a plan to unblock it. No track
is ever shipped before it meets its done-when, whatever that costs in time.

Honest notes:
- **Bootloader** and **everyday apps** are the most achievable.
- **Filesystem** is very hard to get right, because a bug loses people's files. It gets the heaviest testing of anything here.
- **Web browser engine** is the biggest single project on this list, bigger than the kernel. HTML, CSS and JavaScript each take years. It is a long-running track, and a borrowed browser ships until ours passes its tests.

## What only the owner can provide

Some things can't be done from CI and need Ben:

- **Real hardware:**
  - booting each milestone from USB on a real PC;
  - a dedicated KVM host from Phase 1: an x86-64 machine with KVM that runs nothing else, for the clock-drift gate and the pre-hardware trend report (QEMU with CPUID level at least 0x15 and an explicit `tsc-frequency`);
  - the reference machines in [design/benchmarks.md](design/benchmarks.md), set up as dedicated runners for the performance gate: the reference desktop from Phase 1 (real-hardware boot) and as a dedicated runner by Phase 2, a second identical reference desktop by Phase 6 (long runs, starting with the 24-hour audio runs), the reference laptop on the rig by Phase 6 (results over a USB Ethernet adapter on the rig network, reset by a relay that disconnects the internal battery and the AC adapter together, power-on by a second relay across the power-button contacts), the rest by Phase 5; every desktop reference machine needs a native COM header on a Super I/O chip (legacy I/O ports and IRQ, DCD wired), a board-selection requirement, because USB-serial and network paths need drivers that don't exist before Phase 6;
  - an Intel and an AMD reference machine by Phase 3, for the 32-bit entry test;
  - the reference desktop's discrete GPU model chosen and recorded before Phase 5 starts (the Phase 8 driver targets it);
  - the benchmark controller host (a Raspberry Pi or similar, with a power relay, serial capture, an isolated network, and a GPS receiver whose PPS output is wired to each runner's UART DCD pin for the bare-metal clock-drift test) by Phase 2;
  - a multi-node reference machine (2-socket, or an AMD EPYC in NPS2 or NPS4) as soon as it can be had, until which NUMA is tested for function only;
  - by Phase 4a: a crash-test machine (32 cores, 128 GiB RAM, local NVMe) that runs the nightly crash states, needed at Phase 4a entry because the nightly target is measured on it then; a PCILeech-class FPGA DMA board, run in a D1 reference machine whose firmware has pre-boot DMA protection; an Intel 7- or 8-series machine for the USB port-routing test and an AMD chipset machine for the legacy-emulation passphrase test; a reference machine with a hot-pluggable NVMe or Thunderbolt device for the surprise-removal test; a relay power-cut rig and 3 drive models (ext4 over LUKS2 in 4a, then the filesystem track);
  - by Phase 6: a programmable USB board that runs a keystroke-injection script, a Thunderbolt NVMe enclosure, and reference machines with a software-managed USB4 port and with an ICM Thunderbolt controller;
  - an input-latency rig (USB HID microcontroller and photodiode) by Phase 7;
  - reference machines with AMD SME and Intel TME by Phase 11.
- **Services:** a public transparency log and at least 2 independent witnesses, run by parties other than the release signers, before Phase 4b starts (a 4b entry condition).
- **Signing keys:** hardware tokens for the offline root key (2 of 3) before the first public release, and for the config-signing key (2 of 3) by Phase 4b.
- **Outside audits** at the end of Phases 1, 3, 4a and 4b and before 1.0 (volunteers or funding).
- **Accounts:** shim review submission and Microsoft signing (Phase 4b tests path 1 with a test CA enrolled in db, so it never waits for them), and repository settings.

Until a dependency arrives, the work that needs it is reported as "not yet
measured" or "not yet done", never claimed.
